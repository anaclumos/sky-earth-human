# S4: input click spike

Proves what `UIInputViewAudioFeedback` plus `UIDevice.current.playInputClick()`
does on the iOS Simulator for a keyboard extension with `RequestsOpenAccess`
false and no in-app sound toggle, and compares it against the
`AudioServicesPlaySystemSound(1104)` path version 1.1 used.

Status: simulator part complete, including a second view-placement variant
requested after review of the first pass. All eight conditions (two view
placements times four `enableInputClicksWhenVisible` by Settings Keyboard
Sound combinations) and the `AudioServicesPlaySystemSound(1104)` comparison
are confirmed with log evidence. The owner haptics section below is a
checklist only, since the simulator has no Taptic Engine.

## Environment

- Simulator device: `spike-S4`, UDID `6E19BDE5-9903-48A3-B63B-12DEE861BB75`, iPhone 17 Pro.
- iOS runtime: iOS 27.0 (27.0 - 24A5390f), `com.apple.CoreSimulator.SimRuntime.iOS-27-0`.
- Xcode: 27.0, build 27A5228h, `DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer`.
- Throwaway project: `scratchpad/spikes/S4/spike-s4`, outside the repo, not committed.
- Targets: `spike-s4` (host app, bundle `sh.cho.spike-s4`), `spike-s4-keyboard` (extension, bundle `sh.cho.spike-s4.keyboard`, `RequestsOpenAccess` false), `spike-s4-uitests`.
- Derived data: `scratchpad/dd/S4`.

## Method

- The keyboard extension installs a `UIInputView` subclass (`ClickInputView`) conforming to `UIInputViewAudioFeedback`, with `enableInputClicksWhenVisible` hardcoded per condition and rebuilt between conditions. Restored to `true`, the 2.0 decision default, after the last capture.
- Four buttons in the extension's SwiftUI root view each call one API and log through `os.Logger` (subsystem `spike.s4`, category `feedback`) immediately before and after the call. CLICK calls `UIDevice.current.playInputClick()`. LEGACY calls `AudioServicesPlaySystemSound(1104)`. HAPTIC calls `UIImpactFeedbackGenerator(style: .light)`. SELECTION calls `UISelectionFeedbackGenerator()`.
- `spike-s4-uitests/EnableKeyboardUITests.swift` is an XCUITest against `com.apple.Preferences`. It adds the spike-S4 keyboard under Settings > General > Keyboard > Keyboards > Add New Keyboard, where no Allow Full Access screen appears, matching `RequestsOpenAccess` false. It also toggles the keyboard click sound setting.
- iOS 27's Settings app has no top-level "Sounds & Haptics" screen. The keyboard click sound toggle was located live by dumping the accessibility tree. It is at Settings > General > Keyboard, a `Switch` with accessibility identifier `keyboard-audio`, label "Sound", alongside a separate `Switch` identifier `KeyboardVisceral`, label "Haptic Feedback". The toggle test sets the switch, force-quits Settings, relaunches, and re-reads the value from a fresh query before trusting it. A same-session re-read of the same `XCUIElement` was unreliable on this build.
- `SpikeKeyboardInteractionUITests.testTapAllFeedbackButtons` focuses the host app's text field, switches to the spike-S4 keyboard by tapping the globe key once and waiting, then taps CLICK, LEGACY, HAPTIC, SELECTION in order with a 0.3s gap. This simulator has 4 enabled input modes (English, Korean 2-beolsik, Emoji, spike-S4). A single tap was empirically sufficient and reliable once the wait was made generous, see Deviation below.
- Evidence comes from `xcrun simctl spawn <udid> log stream --level debug` running concurrently in the background, filtered for the `spike.s4` subsystem, click and audio related keywords, and the `systemsoundserver-simd`, `mediaserverd`, `coreaudiod` processes. Output is captured to a file under `scratchpad/spikes/S4/logs/` and grepped after each run.

### View placement: two variants

The first pass installed `ClickInputView` as an ordinary subview of `self.view` (`view.addSubview(clickInputView)`), never touching `self.inputView`. A review of that result questioned whether the system inspects `self.view`'s subviews at all for `UIInputViewAudioFeedback`, or only `self.inputView` specifically, since the observed `usesKeyClicks = NO` was consistent with the system never finding a conforming view. This was checked against the live SDK headers and the live Apple documentation JSON, not from memory.

SDK header quotes, from `iPhoneSimulator27.0.sdk/System/Library/Frameworks/UIKit.framework/Headers`:

- `UIDevice.h`: `- (void)playInputClick ... // Plays a click only if an enabling input view is on-screen and user has enabled input clicks.`
- `UIDevice.h`: `@property (nonatomic, readonly) BOOL enableInputClicksWhenVisible ... // If YES, an input view will enable playInputClick.`
- `UIInputViewController.h`: `@property (nullable, nonatomic, strong) UIInputView *inputView;` (no inline doc comment in the header itself).

Apple Developer Documentation quotes, fetched live from the documentation JSON API (`developer.apple.com/tutorials/data/documentation/...`):

- `UIInputViewController/inputView` Discussion: "When you use an input view controller subclass as the primary view controller for a custom keyboard, this property's UIInputView object is initially empty. To display your keyboard's user interface, add controls and views to the inputView property."
- `UIDevice/playInputClick()` Discussion: "Use this method to play the standard system keyboard click in response to a user tapping in a custom input or keyboard accessory view. A click plays only if the user has enabled keyboard clicks in Settings > Sounds, and only if the input view is itself enabled and visible. To enable a custom input or accessory view for input clicks, perform the following two steps: 1. Adopt the UIInputViewAudioFeedback protocol in your input view class. 2. Implement the enableInputClicksWhenVisible delegate method to return true."
- `UIInputViewAudioFeedback` Overview: "Implement this protocol in your custom subclass of UIView that you associate with your custom input nib file. ... Implementation of this protocol is optional but expected."

This confirms the review's concern. Apple's own `inputView` documentation names the `inputView` property, not an arbitrary subview of `self.view`, as where a custom keyboard's UI belongs. Variant A (the original code, `view.addSubview(clickInputView)`, never assigning `self.inputView`) did not follow this. Variant B assigns `self.inputView = clickInputView` at the top of `viewDidLoad`, before adding the SwiftUI hosting view as `clickInputView`'s subview, and does not touch `self.view` separately. `viewDidAppear` now logs `self.inputView`'s class and whether `self.inputView === self.view`, to confirm the assignment took effect. Live result: `self.inputView class=ClickInputView, self.view class=Optional<UIView>, inputView===view=true`. `self.view` and `self.inputView` are the same object once assigned, which also empirically answers the ambiguity in Apple's Discussion text about whether `self.view` needs separate wiring, it does not, `UIInputViewController` returns the assigned `inputView` back out of `self.view` for a keyboard extension. Variant B's keyboard renders and its buttons are tappable exactly like Variant A's, confirmed by the same `testTapAllFeedbackButtons` UI test passing unmodified.

Variant A's four conditions (rows below) stay as a recorded negative result, they are not re-run. Variant B's four conditions are a new, separate sweep, logs named `cond{E,F,G,H}-variantB-*.log`.

### Deviation from plan

- The globe-key tap to switch keyboards was flaky on the first pass, timing out waiting for the CLICK button. Traced to two causes, both fixed in the harness rather than worked around. First, this simulator has 4 enabled input modes, not 2, so a cold extension launch plus scene handoff can take longer than the original 10s wait. Second, this machine runs several other concurrent xcodebuild and simctl jobs from sibling spike nodes in the same rebuild wave, adding contention. Fixed by tapping once and waiting up to 45s, and by never blindly retrying the tap, since a second tap on a 4-keyboard cycle does not retry the switch, it cycles further away from spike-S4.
- The plan's wording "Sounds and Haptics Keyboard Feedback Sound" describes the setting's function. The literal iOS 27 location differs from stock Settings on earlier iOS releases, since this simulator build has no dedicated "Sounds & Haptics" root screen. Verified live, not from memory or docs, by dumping the Settings accessibility tree.

## Evidence obtained and not obtained

Obtained:

- `os.Logger` call-site evidence (subsystem `spike.s4`) for every button tap in every condition run, proving the call happened and returned without throwing or hanging.
- `xcrun simctl spawn <udid> log stream` evidence of the simulator's dedicated `systemsoundserver-simd` process actually resolving and queuing `key_press_click.caf` for `AudioServicesPlaySystemSound(1104)`, with a measured server-side play time (`SystemSoundServerPlayActionID took 2 ms`).
- Negative evidence for `playInputClick()`. No XPC connection, no audio file resolution, no `systemsoundserver-simd` log line of any kind appears between "CLICK tapped" and "CLICK returned" in any condition, in either view placement. The simulator's `usesKeyClicks` internal flag stays `NO` on the `UIInputViewSet` even when `enableInputClicksWhenVisible` is `true`, the keyboard is the visible first responder, and `self.inputView` is confirmed to be the conforming view.
- All four `enableInputClicksWhenVisible` by Settings Keyboard Sound combinations were run for both view placements, eight runs total. The negative result for `playInputClick()` is identical in all eight. The positive result for `AudioServicesPlaySystemSound(1104)` is identical in all eight. Neither call's behavior is conditioned on `enableInputClicksWhenVisible`, the Settings switch, or view placement on this simulator build.
- Direct evidence that the `UIInputViewSet` logs inspected for `usesKeyClicks` are tracking a private system class, `_UIKBCompatInputView`, not `ClickInputView`, even in Variant B where `ClickInputView` is confirmed to be both `self.inputView` and `self.view`. This is evidence toward, not proof of, the `usesKeyClicks` log line being a simulator-side aggregate signal that does not directly reflect a third-party extension's own input view instance.

Not obtained:

- No macOS-side audio tap or `sample` of `coreaudiod` confirming or ruling out sound actually reaching the host speaker for the LEGACY path. The `systemsoundserver-simd` evidence shows the simulator's own play pipeline was engaged, not that audio was audible on the Mac.
- No `AVAudioSession` notification was observed for either path. The keyboard extension never activates an `AVAudioSession`, and neither `playInputClick()` nor `AudioServicesPlaySystemSound(1104)` triggered one on the simulator in this project.
- No explanation, beyond the `_UIKBCompatInputView` observation above, for why `playInputClick()` produces no server-side trace even under the documented-correct Variant B placement. That would need either a physical device repeat of this harness or deeper reverse engineering of the simulator's keyboard-click plumbing, both out of scope for this spike.

## Finding

- The review's placement concern was correct as a documentation matter. Apple's live `UIInputViewController.inputView` documentation states plainly, for the custom-keyboard case: "To display your keyboard's user interface, add controls and views to the inputView property." Variant A (the first pass) never touched `self.inputView` and instead added `ClickInputView` as a plain subview of `self.view`. That is not the documented pattern, and the recorded negative from Variant A alone would not have been strong enough evidence.
- Variant B fixes this. `self.inputView = clickInputView` is assigned before any other view work, and `viewDidAppear` confirms live, in every one of its four runs, `self.inputView class=ClickInputView, self.view class=Optional<UIView>, inputView===view=true`. `UIInputViewController` returns the assigned `inputView` back out through `self.view` for a keyboard extension, so no separate `self.view` wiring was needed once `self.inputView` was set. The keyboard renders and behaves identically to Variant A from the user's perspective.
- Despite the corrected, documented-correct placement, the observed result is unchanged. `UIDevice.current.playInputClick()` produces no observable simulator audio activity in any of Variant B's four combinations either, no XPC connection to the simulator's system sound server, no resolution of a click sound asset, and `usesKeyClicks` stays `NO` on the scene's `UIInputViewSet` throughout, same as Variant A.
- The same extension's `AudioServicesPlaySystemSound(1104)` call, under all eight combinations across both variants, reliably reaches `systemsoundserver-simd` and queues the real `key_press_click.caf` asset in about 2ms every time.
- K7 must still use the Variant B placement (`self.inputView = clickInputView`, adding the keyboard's UI as its subview) for the production keyboard, because it is what Apple documents, and because a physical device may honor `usesKeyClicks` correctly only when the protocol is adopted on the actual `inputView`, something this simulator cannot rule in or out either way given the identical result across both placements here.
- This remains a simulator-only result for `playInputClick()` itself. It shows the call produces no server-side trace in this environment under either placement, not that it is a no-op on a physical device. Apple's own documentation says it "plays the standard keyboard click sound" and defers to the user's Settings > Sounds > Keyboard Clicks preference.
- The 1.1 to 2.0 migration from `AudioServicesPlaySystemSound(1104)` to `playInputClick()` cannot be verified as sounding equivalent using only this simulator, under either placement. It needs the owner haptics and sound pass on a physical device, see below, or a device-side repeat of this same harness.

## AudioServicesPlaySystemSound(1104) comparison row

See the comparison tables above, one per variant. Under the same `RequestsOpenAccess` false constraint, the 1.1-era legacy call visibly reaches the simulator's system sound server and plays the real keyboard click asset regardless of `enableInputClicksWhenVisible`, the Settings Keyboard Sound switch, or view placement. `playInputClick()` in the same extension, same taps, produces no comparable evidence in any of the eight conditions tested across both variants.

## Owner haptics test

Apple documents nothing about haptics inside keyboard extensions. This is a checklist only, to run on a physical device by the owner, not something the simulator can answer, since the simulator has no Taptic Engine.

Steps:

1. Build and install the spike (or the real keyboard target) on a physical iPhone, with the keyboard extension's `RequestsOpenAccess` false and Full Access left off in Settings.
2. In Settings, set the Keyboard Feedback Haptic toggle (the Settings > General > Keyboard > Haptic Feedback equivalent on that iOS version) ON. Open the keyboard in a text field and tap a key that calls `UIImpactFeedbackGenerator(style: .light).impactOccurred()` inside the extension process. Record whether the Taptic Engine fires, and whether the OS plays any accompanying sound regardless of the separate Sound switch.
3. With Full Access still off, set the same haptic setting OFF. Repeat the same key tap. Record whether the Taptic Engine still fires. This checks whether the extension can drive haptics independent of the system keyboard's own haptic setting, since `UIImpactFeedbackGenerator` is a generic UIKit API, not a keyboard-specific one.
4. Repeat both haptic-setting states with the device's Silent/Ring switch in both positions, and with System Haptics (Settings > Sounds & Haptics on real hardware, or Accessibility > Touch > Vibration) toggled, and record each combination. These device-wide switches are not accessible in the simulator at all.
5. For each of the above, also record whether `impactOccurred()` throws, silently no-ops, or fires but feels different in strength than the same call made from a normal foreground app. Keyboard extensions run in a separate, memory-constrained process, and haptics could plausibly be suppressed or altered by the system for that process class.
