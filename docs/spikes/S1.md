## Spike project shape

- `SpikeS1.xcodeproj` with three targets: `SpikeHost` (bundle `sh.cho.spike-s1x`), `SpikeKeyboard` (bundle `sh.cho.spike-s1x.keyboard`), `SpikeUITests`.
- `SpikeHost` is a SwiftUI app with a UIKit `UITextField` (`uiTextField`) for focus.
- `SpikeKeyboard` has `RequestsOpenAccess` false, `IsASCIICapable` false, `PrimaryLanguage` `ko-KR` in its Info.plist. It calls `requestSupplementaryLexicon(completion:)` in `viewWillAppear`, and again on a manual `AGAIN` button tap. Every request and every returned entry is logged through `Logger` (subsystem `spike.s1x`, category `lexicon`) with the sequence number, phase, elapsed time, entry count, and each entry's `userInput`/`documentText` plus their Unicode scalar breakdown (`U+XXXX` per code point).
- Evidence is read back with `xcrun simctl spawn <udid> log stream --level info --predicate 'subsystem == "spike.s1x"'`.
- `--level info` is required. A stream without it drops every `Logger.info` line.

## Project history: why the throwaway project was rebuilt

First attempt, abandoned:

- Hand-assembled the app and keyboard extension bundles directly with `xcrun swiftc` and manual `codesign --sign -`, no `.xcodeproj`, scripted by `scratchpad/spikes/S1/build.sh` (kept on disk, superseded, not deleted).
- The keyboard extensions registered with PluginKit and could be toggled on in Settings.
- The toggle never took effect. `UITextInputMode.activeInputModes` and globe-key cycling never included them, before or after a full simulator reboot and a `simctl install` reinstall.
- Working hypothesis at the time, now retracted below, a bundle id prefix collision, `sh.` colliding with the deprecated ISO 639-1 code for Serbo-Croatian, by analogy with a documented iOS 13 case for `mn.`/`to.` prefixes.

That hypothesis was wrong. Sibling spike nodes on the same iOS 27.0 runtime (S2, S4) enabled third-party keyboards successfully using real `.xcodeproj` targets built with `xcodebuild`. That comparison isolated the real cause:

- A single-keyboard-extension app's row in Settings > General > Keyboard > Keyboards > Add New Keyboard adds and enables the keyboard with one tap, no separate switch.
- Doing this through `SpikeS1.xcodeproj`'s `SpikeHost`/`SpikeKeyboard` targets set `AppleKeyboardsExpanded = 1` in the Apple Global Domain alongside the `AppleKeyboards` array entry.
- The earlier hand-assembled build had two keyboard extensions in one app. Settings routes that through a sub-page of individual switches instead of a single tap.
- A plain `.tap()` on that switch did nothing at all. A `coordinate(withNormalizedOffset:)` tap was needed to flip it in the UI.
- That switch added the bundle id to `AppleKeyboards` but never set `AppleKeyboardsExpanded`. Without that key the keyboard is listed but not actually active, which matches every symptom recorded in the abandoned attempt.
- Verified with `xcrun simctl spawn <udid> defaults find AppleKeyboards`. After the hand-built app's switch toggle, the result had no `AppleKeyboardsExpanded` key at all. After the Xcode-built app's single-tap add, the result was `AppleKeyboardsExpanded = 1` alongside the array.
- Second, independent mechanic in the same category. iOS shows a one-time "Quickly Change Keyboards" tutorial overlay with a `Continue` button the first time a multi-keyboard device's globe key would be used. It intercepts the first tap on `Next keyboard` if not dismissed first.
- Third mechanic, single-tap globe cycling only rotates through a short recently-used list. Observed system English and system Korean, alternating over 10 taps, never reaching the third-party keyboard.
- Reaching a keyboard that has not been recently used needs a long press (`press(forDuration:)`) on the `Next keyboard` button. That opens a picker listing every enabled keyboard by name, `Spike S1X` then U+2014 then `SpikeHost, Korean` in this project, then tapping that row switches to it.

None of this touched the real app's Fixed Point bundle id (`sh.cho.sky-earth-human.keyboard`). The collision theory in the abandoned attempt is retracted.

## Q2: Does PrimaryLanguage change the entries (ko-KR vs en-US)

Two builds, not one build read at runtime.

- `SpikeKeyboard`'s `NSExtensionAttributes` are static plist content with no code path to branch on at launch, and a single `.appex` cannot declare two `NSExtension` dictionaries, so the only way to compare `PrimaryLanguage` values is to rebuild.
- Both builds used the exact same `KeyboardViewController.swift`, the exact same bundle id (`sh.cho.spike-s1x.keyboard`), the exact same `RequestsOpenAccess` false and `IsASCIICapable` false.
- The only line changed between builds was `PrimaryLanguage` in `SpikeKeyboard/Info.plist`, from `ko-KR` to `en-US` and back.
- Each change was followed by `xcodebuild build-for-testing`, `xcrun simctl install <udid> SpikeHost.app`, and a fresh `requestSupplementaryLexicon` capture.
- The same Text Replacement shortcuts were already committed in Settings for both builds, holding that variable constant too.

| | ko-KR build | en-US build |
| --- | --- | --- |
| `textInputMode?.primaryLanguage` logged on `APPEAR` | `ko-KR` | `en-US` |
| Entry count | 34 | 34 |
| Entry set | Same 34 pairs as en-US, order differs | Same 34 pairs as ko-KR, order differs |

- Diffing the two entry lists after sorting both by `userInput -> documentText` produces an empty diff. The two builds return the identical set of 34 `userInput`/`documentText` pairs.
- Only the order `requestSupplementaryLexicon` returns them in differs between builds, and even between separate calls within the ko-KR build across the Q3 session.
- `PrimaryLanguage` had no observable effect on which entries came back, for this simulator's fixed set of stock Contacts and this session's Text Replacement shortcuts, one of which has a Hangul `userInput`.

## Q3: Refresh timing after adding a Text Replacement shortcut mid-session

Single XCUITest, `testRefreshTiming`, step by step:

- Focus the host field, bring `SpikeKeyboard` up with a long press on `Next keyboard` then a tap on its picker row.
- Tap `AGAIN` once for a baseline read.
- Switch to `com.apple.Preferences`. The host app backgrounds, the text field keeps first responder, so the keyboard is still "showing" per Apple's documented suspend-not-resign multitasking behavior.
- Add a brand new Text Replacement shortcut, `brbnow` -> `Be right back`, through Settings > General > Keyboard > Text Replacement > Add, then Save.
- Call `host.activate()` back to the host app. `resignFirstResponder()` is never called and the keyboard is never dismissed at this point.
- Only after that, dismiss the keyboard with `host.terminate()`. This host app has no in-app dismiss affordance and no system "Dismiss keyboard" button appears for a custom keyboard on iPhone.
- Reappear with `host.launch()` and refocus the field, to compare against a real dismiss-and-reappear cycle.

`requestSupplementaryLexicon` fires automatically in `viewWillAppear` on every appearance, plus once more per explicit `AGAIN` tap. Log excerpt below, sequence numbers as logged, `count` is the total entry count that call returned:

```
seq=1 phase=viewWillAppear count=33   (baseline, before brbnow existed)
seq=2 phase=manual         count=33   (baseline AGAIN tap)
--- switch to Settings, add brbnow -> Be right back, Save, switch back to host, keyboard never dismissed ---
seq=3 phase=viewWillAppear count=33   (first automatic re-appearance on returning to the host app, brbnow absent)
seq=4 phase=viewWillAppear count=34   (second automatic re-appearance, about 5s later, brbnow present)
seq=5 phase=manual         count=34   (explicit AGAIN tap, brbnow present)
--- host.terminate(), then host.launch() and refocus: a real dismiss and reappear ---
seq=6 phase=viewWillAppear count=34   (fresh process after relaunch, brbnow present)
seq=7 phase=manual         count=34   (explicit AGAIN tap, brbnow present)
```

Entry line for the new shortcut, first appearing at seq=4:

```
S1X|ENTRY|seq=4|i=33|userInput=<brbnow>|documentText=<Be right back>|inputScalars=[U+0062 U+0072 U+0062 U+006E U+006F U+0077]|docScalars=[U+0042 U+0065 U+0020 U+0072 U+0069 U+0067 U+0068 U+0074 U+0020 U+0062 U+0061 U+0063 U+006B]
```

| Question | Answer |
| --- | --- |
| Does the shortcut appear without dismissing the keyboard | Yes, but not on the very first `viewWillAppear` after switching back from Settings (seq=3, still 33). It appeared on the second automatic `viewWillAppear` about 5 seconds later (seq=4, 34), and on every request after that. The keyboard was never dismissed in between, `host.activate()` alone triggered both automatic calls. |
| Does the shortcut appear after dismiss and reappear | Yes, immediately on the first `viewWillAppear` of the fresh process (seq=6). |
| First point the new shortcut is visible | seq=4, an automatic `viewWillAppear`, roughly 5 seconds after the Settings save, without any dismiss having happened |

A Hangul shortcut added earlier in the session (`userInput` `U+3131 U+314F`, `documentText` `U+AC00`) was present in every one of these seven calls (seq=1 through seq=7), confirming a Hangul `userInput` round-trips through `requestSupplementaryLexicon` correctly once committed:

```
S1X|ENTRY|seq=1|i=29|userInput=<[U+3131][U+314F]>|documentText=<[U+AC00]>|inputScalars=[U+3131 U+314F]|docScalars=[U+AC00]
S1X|ENTRY|seq=7|i=31|userInput=<[U+3131][U+314F]>|documentText=<[U+AC00]>|inputScalars=[U+3131 U+314F]|docScalars=[U+AC00]
```

- The `userInput`/`documentText` angle brackets in the log line hold the raw Hangul characters the keyboard logged. They are replaced with their code points here to keep this document Hangul-free.
- The `inputScalars`/`docScalars` fields are the code point dump the log line already carries.
