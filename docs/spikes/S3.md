## Enabling the keyboard on the simulator

Driven by an XCUITest against `com.apple.Preferences` (`SpikeS3UITests/EnableKeyboardUITests`), following Settings > General > Keyboard > Keyboards > Add New Keyboard.

Findings while automating this:

- The search field on the Add New Keyboard screen only matches built-in language keyboards. Typing `SpikeS3` into it returns zero results, confirmed live (`search-result.png`, `search-result2.png` in the scratch project). Third-party keyboards are not searchable there.
- The Add New Keyboard list is one continuous alphabetically sorted list of every language keyboard iOS supports, several hundred rows, starting after a short curated "Suggested Keyboards" group. Confirmed live by scrolling the table to its end: the language section's last row is `Zulu`.
- Third-party keyboards belonging to installed apps are not interleaved alphabetically with the language keyboards. They sit in a further section reached by scrolling past the language list. How far varies. On the phone simulator the row existed in the accessibility tree immediately, with no scrolling needed at all. On the pad simulator it took genuine scrolling. The spike test queries by label across every element type first (`.exists` with no scroll), then falls back to `swipeUp(velocity: .fast)` on the table, bounded and checked periodically.
- iOS 27 beta has an accessibility quirk. Some UILabel-based Settings rows report an "Automation type mismatch" (computed `.other` from legacy attributes vs `.staticText`/`.button` from the modern attribute). Querying `.buttons` for the third-party keyboard row silently never matched even when the row was present. Broadening to `settings.descendants(matching: .any)` fixed it. Worth remembering for any future Settings automation in this SDK.
- iPad Settings is a split view. The sidebar row and the detail pane's large title can carry the identical label (both say "General", for example), so a plain `staticTexts["General"]` lookup is ambiguous on iPad (`Multiple matching elements found`) even though the same call is unambiguous on iPhone's single-column navigation. Fixed by picking the leftmost on-screen match, which is always the tappable row, not the heading.
- iPad Settings also keeps the previous screen's table mounted behind the Add New Keyboard sheet, so `settings.tables.firstMatch` can resolve to the wrong table. Swiping it produced no visible change for 700 swipes because it was scrolling the hidden "Keyboards" list, not the sheet. Fixed by picking the table that contains the search field, which only the Add New Keyboard sheet has.
- The real blocker on iPad turned out to be nothing about the UI automation. The host app (and therefore its embedded keyboard extension) was simply not installed on the pad simulator. `xcrun simctl spawn <udid> pluginkit -m -p com.apple.keyboard-service` listed the extension on the phone but returned nothing on the pad, and `xcrun simctl listapps` confirmed only the UI test runner app was present there, not `sh.cho.spike-s3`. `xcodebuild test -only-testing:...` did not reinstall the host app dependency on that destination, likely stale derived-data state left over from an earlier interrupted run. Fixed by installing the already-built `SpikeS3App.app` directly with `xcrun simctl install <pad-udid> .../SpikeS3App.app`, after which `pluginkit` listed the extension and the same test passed. This is the one finding worth remembering above the others. When a custom keyboard silently never appears in Settings on a given simulator, check `pluginkit -m -p com.apple.keyboard-service` before assuming it is a UI automation problem.
- Result: `EnableKeyboardUITests.testEnableKeyboard()` passed on both simulators, confirmed with screenshots of Settings > Keyboards showing `SpikeS3` as an enabled keyboard (`keyboard-enabled-phone.png`, `keyboard-enabled-pad.png`). On the pad, two extra language keyboards (Tongan, Filipino Baybayin) ended up enabled as a side effect of the earlier mis-scrolling against the wrong background table. Harmless for the height measurements, just means more "next keyboard" taps to cycle to SpikeS3.
- A single tap on the globe ("Next keyboard") key only cycles between the two most recently used input modes on this iOS beta, confirmed live by tapping it 10 times in a row and seeing it strictly alternate between English and Korean, never reaching Emoji or SpikeS3. A long press (`press(forDuration: 1.2)`) opens the full keyboard picker menu instead, which lists every enabled keyboard by name. Tapping `SpikeS3` there switches directly. `HeightMatrixUITests` uses the long press.

Status: keyboard enabled and height matrix measured on both simulators, both orientations. Full gate met.

The offset over the requested constant is constant across all three heights on a given device and orientation, so it is not noise. It is fixed system chrome added outside the keyboard extension's own view. On the phone it is +92 in portrait and +34 in landscape (varies by orientation). On the pad it is a flat +75 in both orientations. Every one of the 8 runtime changes reported animation duration `0.0`, meaning the height snapped instead of animating, with this spike's current `applyHeight()` (set the constant, then `setNeedsLayout()` and `layoutIfNeeded()` called synchronously, not inside a `UIView.animate` block).

## Constraint priority and activation pattern

Apple's Custom Keyboard guide describes the pattern this spike follows: add a height constraint to the input view controller's own view, and note that the constant can change any time after the view first draws.

> "You can adjust the height of your custom keyboard's primary view using Auto Layout ... To adjust a custom keyboard's height, change its primary view's height constraint ... In iOS 8.0, you can adjust a custom keyboard's height any time after its primary view initially draws on screen."
> Source: [Custom Keyboard guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html)

Apple's own sample does not name a specific priority. It just calls `addConstraint:` on the view, which defaults to `.required` (1000). This spike instead uses:

```swift
let constraint = view.heightAnchor.constraint(equalToConstant: value)
constraint.priority = UILayoutPriority(999)
constraint.isActive = true
```

created once on first use and mutated by `constant =` on every later call, exactly as the Apple guide describes for updates after the first draw. Priority 999 (one below required) worked cleanly across every measurement above: 4 device/orientation combinations, 3 heights each, 12 layout passes total, with zero Auto Layout "Unable to simultaneously satisfy constraints" warnings in any test log. Activating with `isActive = true` on first creation and only touching `.constant` afterward, rather than deactivating and recreating the constraint, is what kept the updates snapping cleanly instead of momentarily conflicting with the system's own container constraints.

## iPhone vs iPad differences

- The system reserves extra vertical space outside the keyboard extension's own view, and how much differs by device. iPhone 17 Pro: +92pt in portrait, +34pt in landscape. iPad Pro 11-inch (M4): a flat +75pt in both orientations. A keyboard that wants an exact on-screen height cannot rely on the height constraint constant alone. It has to account for this fixed, device- and orientation-dependent offset itself, which is not documented by Apple's height-constraint guide.
- The extra chrome looks different on each device, visible directly in the screenshots. On the phone it is a darker bottom strip carrying the globe (next keyboard) and dictation microphone controls, visible in `phone-portrait-default-216.png` and `phone-landscape-default-216.png`. On the pad it is a top strip carrying undo, redo, and paste controls, with no comparable bottom strip, visible in `pad-portrait-default-216.png` and `pad-landscape-default-216.png`.
- iPad's offset does not change between portrait and landscape. iPhone's does (92 vs 34). Why is not measured in this spike, see Open questions below.
- iPad Settings itself behaves differently from iPhone Settings during the enabling flow (split view with an ambiguous "General" label, and a previous screen's table left mounted behind the Add New Keyboard sheet), both described above. Neither is specific to the height constraint question, but both were required to get to a working iPad measurement at all.
- Keyboard switching behavior (globe key single tap only alternating between the two most recent input modes, requiring a long press to reach a third or fourth keyboard) was the same on both devices. Not an iPhone/iPad difference, noted here only because it surfaced during the same round of testing.

## Open questions

- Why the phone's offset changes by orientation (+92 portrait, +34 landscape) while the pad's does not (+75 both) is not measured here. A plausible cause is the home indicator's bottom safe area, which differs by orientation on iPhone, but this spike only read the host's `keyboardWillChangeFrameNotification` frame, not `view.safeAreaInsets` or the input view controller's own window insets in each orientation, so that cause is unconfirmed. Measuring it would mean logging `KeyboardViewController.view.safeAreaInsets` and the extension window's safe area at each `viewDidLayoutSubviews()` call in both orientations and checking whether the numbers add up to 92 and 34.
- Whether the pad's top strip (undo, redo, paste) is Apple's documented keyboard shortcuts bar, and whether it can be suppressed or accounted for programmatically, is not confirmed against any Apple documentation page. The screenshots only establish that it is there and that its height is a fixed 75pt in both orientations.
