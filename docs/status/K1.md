## Model surface

```swift

  private(set) var keyboardType: KeyboardType

```

- `KeyboardModel.swift` imports `Observation` and `UIKit` only. It does not import `HangulEngine`. Node W1 links the package and node K3 maps `HangulKey` onto the engine's `Key`.
- Every action reaches `KeyActionHandler.handle`. The model then applies only its own state, which is the keyboard type, the symbol page and the dismiss closure. It never decides text.
- Feedback mapping applied by the model before forwarding. `.delete` plays `delete`. `.space`, `.returnKey`, `.dismiss`, `.switchKeyboard` and `.nextSymbolPage` play `modifier`. `.hangul`, `.insert` and `.cycle` play `input`. This is the v1.1 mapping in `archive/v1 keyboard/KeyboardOptions.swift`. Haptics on every kind when the setting is on, which node K7 owns.
- Delete repeat deletes once the moment it starts, then a cancellable `Task` fires every 100 ms, the v1.1 timer interval. `KeyboardView` starts it from the long press on a delete key and cancels it when the press ends or the view disappears. The delete at the start is what makes a hold that ends between the threshold and the first tick still remove a character.
- `reloadSettings()` calls `SettingsReader.reload()` then re-reads key size and the prediction toggle. `KeyboardView` calls it in `onAppear`. Node I1 calls it again on foreground.
- The composition root supplies `showsNextKeyboardKey` from `UIInputViewController.needsInputModeSwitchKey`, the dismiss closure and the globe configuration closure. The globe key is absent from the rows when `showsNextKeyboardKey` is false.

## Key view and the long press

- `KeyButton` renders a `Button` whose label is `KeyFace`, and puts the accessibility identifier, the Korean label and the `isKeyboardKey` trait on that button.
- The button carries `KeyButtonStyle`, a `PrimitiveButtonStyle`, so SwiftUI installs no tap of its own.
- `ButtonStyle` is the wrong protocol here. It applies "standard interaction behavior", and the standard tap is exactly what has to be replaced.
- A style is not a `View`, so `@State` cannot live on `KeyButtonStyle`. The private `KeyButtonSurface` holds `isPressed` and `didLongPress` and is the style's whole body.
- `onLongPressGesture(minimumDuration: 0.35, maximumDistance: 20)` drives every branch inside the surface.
- `onLongPress` is optional. It is nil for a key that has nothing to do on a long press, and the threshold closure returns early, so the press is not claimed and the lift still raises the button action.
- `KeyboardView.longPress(for:)` decides. The delete key gets the repeat, a key whose descriptor carries a `longPressAction` gets `model.longPress(key)`, and every other key gets nil.

| Event | Key with a long press | Key without |
| --- | --- | --- |
| Touch down | `onPressingChanged(true)`, `isPressed` true, opacity 0.5 | same |
| 0.35 s elapsed with the finger still down | `perform`, `didLongPress` true, `onLongPress()` | `perform` returns early, nothing runs |
| Lift | `onPressingChanged(false)`, `onLongPressEnded()`, no button action | `onPressingChanged(false)`, `configuration.trigger()`, which raises `onPress` |
| Lift before 0.35 s | `onPressingChanged(false)`, `configuration.trigger()` | same |

- The threshold stays 0.35 s, measured rather than assumed. Presses of 0.1, 0.2 and 0.3 s are taps, presses of 0.4 and 0.5 s are long presses.
- The delete key is the only key whose long press has no `longPressAction` behind it. Its long press is the repeat, which `KeyboardView` starts and stops.
- The `Button` stays, so the key keeps the button accessibility element and its default activation. `-[NSObject accessibilityActivate]` on the key's live accessibility node, which is what VoiceOver performs on a double tap, returns true and raises `onPress` once.
- A raw gesture would have needed its own `accessibilityAction`, since Apple's own guidance is to reach for `Button` instead of a tap gesture for anything button shaped.
