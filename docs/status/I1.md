## What the composition root is

`KeyboardViewController` holds two eager stored properties and seven lazy ones. The lazy ones are the objects that need the controller or its view, and each one names its own dependencies, so the graph reads top to bottom.

```
AppGroupSettingsReader ---> KeyboardModel, ComposerDriver, SystemFeedbackPlayer
KeyboardInputView ---------> UIInputViewController.inputView, the feedback player's generator
HeightController(view) ----> the extension's own view
MarkedTextInsertionAdapter -> ComposerDriver, LeftoverMarkLifecycle
LeftoverMarkLifecycle ------> viewWillDisappear, viewDidDisappear and viewWillAppear
LexiconPredictionProvider --> PredictionBarProvider.shortcuts, ComposerDriver.shortcuts
CompletionPredictionProvider -> PredictionBarProvider.completions, canExtend back to the driver
PredictionBarProvider ------> ComposerDriver.provider
ComposerDriver -------------> KeyboardModel.actions, KeyboardRootView
KeyboardModel --------------> KeyboardRootView
KeyboardRootView -----------> UIHostingController, pinned to the input view's four edges
```

`KeyboardRootView` is a `VStack(spacing: 0)` of `PredictionBar` over `KeyboardView`. The bar carries its own `HeightMetrics.predictionBarHeight` frame and renders nothing when `isShown` is false, and `KeyboardView` takes `maxHeight: .infinity`, so the bar gets exactly 60 points and the grid gets the rest.

## Leftover mark lifecycle

The wiring `docs/status/K2.md` prescribes in "What K3 and I1 must know", measured there in the conditional pass. `LeftoverMarkLifecycle` holds the two sequences so the unit tests drive the shipped code.

| Hook | Order | Why |
| --- | --- | --- |
| `viewWillDisappear` | `super`, `adapter.hasDocument`, `driver.reset()`, `UserDefaults.standard.set(attached, forKey: "leftoverDocumentAttached")` | The read is taken here, before the host tears the document down, because the flag is what the next appearance decides on. No proxy call here since `d22f22c`. Safari calls this before it blurs its input, and an unmark issued now left the input focused with an empty keyboard, QA finding R07 below |
| `viewDidDisappear` | `super`, `adapter.endLeftoverMark()` | The one unmark of a disappearance runs here since `d22f22c`, after the host's own transition, QA finding R07 below. Nothing follows it, since a second proxy mutation in the same run loop turn as `unmarkText()` loses the text the unmark commits |
| `viewWillAppear` | `super`, read the flag, `removeObject(forKey:)`, `adapter.endLeftoverMark()` only when it read true, then `reloadSettings()` and the lexicon request | After a host resign the proxy has no document at disappearance, and an unconditional unmark on return then commits the text the host still holds marked, with the caret at the start of the field. The key is removed on every read so a stale true cannot leak into a later appearance |
| `textDidChange` | `super`, then `driver.reset()` only when `adapter.hostTextDidChange()` returns true | The host answers two of the keyboard's own calls here, the committing unmark of `settle()` and a newline a return handler declines, and the answer can land after later keys. Only the adapter knows its calls since the host's last view, so it decides, `docs/status/K2.md` finding 8. The root never reads the proxy for this |

- The flag lives in the extension's own `UserDefaults.standard`, not the App Group. `RequestsOpenAccess` is false and K2 measured that it still survives a process rebuild.
- `endLeftoverMark()` is never called from a key handler or from `textDidChange`.
- `driver.reset()` reaches no adapter call, `ComposerDriverTests.resetIsSilent`, so `viewWillDisappear` issues no proxy call and `viewDidDisappear` issues exactly one `unmarkText()` per disappearance, since `d22f22c`, QA finding R07 below.
- `endLeftoverMark()` and a `hostTextDidChange()` that returns true leave the adapter unsettled. The driver queues the next key, calls `settle()`, which issues one `unmarkText()` and holds one run loop turn, and drains the queue after it. The driver owns `adapter.onSettle`, and the root never assigns it and never calls the adapter from a key path.
- A return is `driver.handle(.returnKey)`, which flushes and calls `adapter.insertReturn()`. The newline goes out in its own turn.

### The bug the run found

The first Messages run crashed the extension on every appearance, crash report `~/Library/Logs/DiagnosticReports/keyboard-2026-09-20-213136.ips` and three more with the same trace:

```
EXC_BREAKPOINT, dispatch_assert_queue_fail
swift_task_isCurrentExecutorWithFlagsImpl
closure #1 in KeyboardViewController.viewWillAppear(_:)
thunk for @escaping @callee_guaranteed (@guaranteed UILexicon) -> ()
-[UIInputViewController requestSupplementaryLexiconWithCompletion:]_block_invoke
_xpc_connection_reply_callout
```

UIKit calls the `requestSupplementaryLexicon` completion on an XPC reply queue. `UIInputViewController` carries `NS_SWIFT_UI_ACTOR` in the SDK, so a plain closure literal written inside `viewWillAppear` inherits main actor isolation and Swift 6 puts an isolation check in its prologue, which trapped.

Fix in `1f5c50d`: the closure is marked `@Sendable`, so it does not inherit the actor, and the `UILexicon` is carried to the main actor in a `Task`. `UILexicon` and `UILexiconEntry` are themselves `NS_SWIFT_UI_ACTOR` in the iOS 27 SDK, so they are Sendable and may cross. Every screenshot above was taken after the fix.

## Disagreements between status docs

| Docs | Disagreement | What was shipped |
| --- | --- | --- |
| `docs/status/K4.md` item 3 against the runtime | K4 states that the `requestSupplementaryLexicon` completion runs on the main actor, verified by type checking a subclass that captures a main actor type inside it under Swift 6. The type check does pass, because the SDK marks the class `NS_SWIFT_UI_ACTOR`. At runtime UIKit calls the block on an XPC reply queue and the extension traps | The runtime wins. The closure is `@Sendable` and hops with a `Task`. K4's compile time observation is correct and is not evidence about the calling thread |
| The I1 brief against `docs/status/K6.md` and the merged `PredictionBar.swift` | The brief calls for `PredictionBar(candidates:isShown:onSelect:)`. The merged view takes a fourth argument, `keySize`, added by K6 finding 6 so the bar text matches the key font instead of following Dynamic Type | The merged code wins, `keySize: model.keySize` |
| `docs/status/K8.md` against `docs/status/K6.md` on `predictionBarShown` | K8 says the flag should reflect what the bar actually renders, not `KeyboardModel.isPredictionEnabled` in isolation, because K6 might hide the bar by its own rules. | The I1 brief against the measured test count | The brief expects 43 tests plus whatever I1 adds. 43 was the count on `node/K2`. After merging `rebuild` at `27a6106` the baseline is 56, 58 after `d2cc359` and 64 after `dd143d1` | 111 total, 98 baseline plus 13 |

## Open questions

| Question | State |
| --- | --- |
| Where else the XPC reply queue bites | Only `requestSupplementaryLexicon` is a completion handler in this root. Any future UIKit completion taken on `UIInputViewController` needs the same treatment, and a type check will not reveal it |
| `endLeftoverMark()` and the settings reload in one turn | `viewWillAppear` may call `unmarkText()` and then `reloadSettings()`. K2 finding 1 says no proxy mutation may follow `unmarkText()` in the same turn. `driver.reloadSettings()` only mutates the proxy when the cycle lock changed while a composition was live, and the session is always idle at appearance because `viewWillDisappear` resets it. Safe today, and it would stop being safe if a future node made the reload commit unconditionally. Since K2-fix2 the unmark also leaves the adapter unsettled, and the reload's candidate refresh reads `textBeforeCursor` in that state. That is a read, not a proxy mutation, and the first key goes through `settle()` |
| Text left marked after a host resign | Resolved by node K2-fix2. The flag is false after a host resign, so no call is made on return and the caret stays where the host put it, and the first key's `settle()` commits the kept word there. Measured in the K2-fix2 smoke above |
| A foreground return with no appearance | Not found on iPhone: both measured returns ran `viewWillAppear`. An iPad split view, where the container app and the host can be on screen together, is not measured and is Q1 |
| The prediction bar slot count read by the harness | The harness read two candidates where the screenshot shows three, because it identifies slots by frame and the third sat outside its window. The screenshots are the evidence for the slot count, not the harness log |
| Warm up cost on a device | The warm up call costs 50 ms to 2 s once per process on the simulator. It was not measured on a device, and `docs/status/K5.md` already lists that for S5 |
| Delete repeat against `textDidChange` | `textDidChange` resets the driver when the adapter reads a host change, and K2 measured that a bulk delete burst does produce the callback while a single delete does not. Delete repeat issues one call per 100 ms, so each is a single call, but a host that coalesces them could still fire the callback mid burst. Not exercised on the simulator |
