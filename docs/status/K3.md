## Design

The plan wants the driver logic unit-tested where it is pure, so it is split in two. `InputSession` is a Sendable value type in the engine package with no UIKit. It owns a `HangulComposer` and turns key events into text commands. `ComposerDriver` is the `@MainActor` half in the keyboard target. It maps `KeyAction` onto session events, applies the returned commands to the `InsertionAdapter` in order, and refreshes candidates.

Policies, all of them in `InputSession`:

| Policy | Behaviour |
| --- | --- |
| Space | The first space while composing calls `commit()` and inserts no space. A space with nothing composing inserts one |
| Backspace inside a composition | `backspace()` rewinds one keystroke and the mark is set to the new rendering. An empty result sets the mark to the empty string, which clears it |
| Backspace outside a composition | One `deleteBackward` |
| Plain text, return, punctuation cycle | End the composition first, then act |
| Delete against a mark | Never emitted. S2 measured that one `deleteBackward()` against a marked string clears the whole mark, so the engine rewinds and the caller re-marks |
| Page change, type switch, dismiss | `flush`, which commits the composition and inserts nothing else |

Nothing counts Characters of the composing string anywhere in either file. U+AC38 U+119E is two scalars and one Character, so a Character count would be wrong for a pending araea. The composing text is only ever handed to `setComposing` whole, or replaced whole by a candidate.

## `InputSession` public surface

Verbatim from the emitted module interface at `663050b`, with the module qualifiers the interface printer adds removed.

```swift
public enum InputEvent: Equatable, Sendable {
  case hangul(Key, at: ContinuousClock.Instant)
  case text(String)
  case punctuation(cycle: [String], at: ContinuousClock.Instant)
  case space
  case delete
  case returnKey
  case flush
}

public enum InputCommand: Equatable, Sendable {
  case setComposing(String)
  case commit(String)
  case deleteBackward
}

public struct InputSession: Sendable {
  public let cycleLock: Duration
  public init(cycleLock: Duration)
  public var isComposing: Bool { get }
  public var composing: String { get }
  public mutating func handle(_ event: InputEvent) -> [InputCommand]
}
```

- `handle` returns the commands in the order the adapter must apply them.
- `commit` carries the full text to land. The adapter decides how, which is `unmarkText` plus `insertText` or an equivalent.
- After any event `isComposing` and `composing` say what is currently composing.
- The engine surface used is `HangulComposer.init(cycleLock:)`, `press(_:at:)`, `backspace()`, `commit()`, `isComposing`, `composing` and `Composition`. `canExtend` is not referenced, since its signature is changing.

## `ComposerDriver` and `ShortcutExpander` surfaces

Verbatim from `keyboard/Composer/` at `663050b`, bodies elided.

```swift
@MainActor
protocol ShortcutExpander: AnyObject {
  func expansion(textBeforeCursor: String, composing: String) -> PredictionCandidate?
}

@Observable
@MainActor
final class ComposerDriver: KeyActionHandler {
  private(set) var candidates: [PredictionCandidate]

  init(
    adapter: any InsertionAdapter,
    provider: any PredictionProvider,
    settings: any SettingsReader,
    shortcuts: (any ShortcutExpander)? = nil
  )

  func handle(_ action: KeyAction)
  func apply(_ candidate: PredictionCandidate)
  func reloadSettings()
  func reset()
}
```

- `candidates` is refreshed after every handled action and after `apply(_:)`, from `provider.candidates(textBeforeCursor: adapter.textBeforeCursor, composing: <current composing>)`, and is empty while `settings.isPredictionEnabled` is false. With the setting off the provider is not called at all.
- `apply(_:)` clears the mark, deletes `candidate.replacedLength` committed characters backward, commits `candidate.insertion`, then refreshes. The composition is dropped rather than committed, because the candidate replaces it.
- `reloadSettings()` calls `settings.reload()` and rebuilds the session only when the cycle lock actually changed. An unchanged value leaves a composition in progress untouched. A changed value commits the composition first, so nothing is left marked.
- `reset()` drops the composition and clears the candidates without touching the proxy.
- `HangulKey` is mapped onto the engine `Key` in exactly one place, `ComposerDriver.engineKey(_:)`.

### The candidate contract, ruled here

`replacedLength` counts Characters of committed text before the cursor that the candidate replaces. The composing text is always replaced in full on top of that. A candidate that only replaces the word being composed therefore carries `replacedLength: 0`.

### Shortcut expansion

The expander is asked before space, before return, before plain text that is punctuation, and before the punctuation cycle. It is never asked on a Hangul press or on delete. When it answers, that candidate is applied first and the key's own effect follows.

Punctuation is decided by `Character.isPunctuation`. Measured live against every glyph in the 2.0 layout: `! ? . , ( ) @ : / - * _ % # U+300A U+300B U+300E U+300F " ' U+203B & \ ; { } [ ]` are punctuation; the digits, the backtick, `| < > ~ ^ = + $ U+20A9 U+20AC U+00A3 U+00A5 U+00D7 U+00F7 U+00B0 U+2605 U+2665` and the eight arrows are not.

An expansion ends the composition, so the space that follows one lands as an ordinary space, which is what iOS does after a text replacement. No special case is needed for it.

## The v1.1 punctuation cycle

Read from `archive/v1` at `1fe3471`, not from a summary.

| Fact | Source |
| --- | --- |
| The key carries `.cycle([".", ",", "?", "!"])` on all three pages | `keyboard/KeyboardOptions.swift` lines 336, 378, 414 |
| The action dispatches to `inputEngine.composableInput(candidates:proxy:)` | `keyboard/KeyboardOptions.swift` lines 180 to 182 |
| The cycle itself | `sky-earth-human/Shared/KeyboardInputEngine.swift` lines 90 to 110 |

What lines 90 to 110 do:

- If `state.isEditingLastCharacter` is true and the last Character of `proxy.documentContextBeforeInput` equals the first Character of some candidate, call `deleteBackward()` once and insert `candidates[(index + 1) % candidates.count]`.
- Otherwise insert `candidates[0]`.
- Either way set `state.isEditingLastCharacter = true`, `state.proxyBackup` to what was inserted, and `state.proxyHistory` to empty.

`isEditingLastCharacter` is set true by `simpleInput` (line 31), by `insertHangul` (lines 52 and 85) and by `composableInput` (line 107). It is set false by `deleteBackward` (line 126), by `returnKey` (line 151), by `autocomplete` (line 164) and by `space` through `resetComposition()` (line 142).

**Timing in v1.1: none.** There is no timer, no date, no clock and no interval anywhere in the cycle path. Grepping every Swift file on `archive/v1` for `Timer`, `Date(`, `CACurrentMediaTime`, `DispatchTime`, `ContinuousClock`, `timeInterval` and `Clock` returns hits in exactly one file, `keyboard/HangulView.swift` lines 15 to 88, and those are the delete-repeat timer. The v1.1 cycle stayed open indefinitely, bounded only by that flag and by the character actually sitting before the cursor.

How 2.0 reproduces it, and where it differs:

| Item | v1.1 | 2.0 |
| --- | --- | --- |
| Candidate order and wrap | `.` `,` `?` `!`, modulo the count | Same |
| Replacing the previous mark | One `deleteBackward()` then insert | `.deleteBackward` then `.commit(next)` |
| Window | None | The session cycle lock, the same setting the engine uses for consonant cycling, default 1.0 s. A press at exactly the lock still cycles, matching the engine's `<=` rule from E1 |
| What continues a cycle | The document's last character matching a candidate, so a `.` typed from symbol page one would also be picked up by the cycle key | Only an immediately preceding punctuation press with the same cycle strings. Every other event clears the cycle state |
| Source of truth | `documentContextBeforeInput` | Session state. S2 recorded that `documentContextBeforeInput` omits marked text and can be stale right after a mutation |
| Cycling into a composition | Possible in principle | Impossible. The composition is ended first and a cycling press only ever follows a punctuation press, so no delete lands on a mark |

An expansion between two punctuation presses also restarts the cycle. That was a real defect in the first draft of the driver, fixed in `663050b`: the second press would have emitted a delete against the last character of the expansion.

## `UserDefaults` and Sendable

`SettingsReader` is `Sendable` with a non-mutating `reload()`, so the shape depends on whether `UserDefaults` can be stored.

It cannot. Compiling

```swift
func requireSendable(_ value: some Sendable) {}
func probe(_ defaults: UserDefaults) { requireSendable(defaults) }
```

with `swiftc -typecheck -swift-version 6 -target arm64-apple-ios17.0-simulator` against the iOS 27.0 simulator SDK fails with `error: conformance of 'UserDefaults' to 'Sendable' is unavailable`, and the note points at `@_nonSendable(_assumed)` on `@interface NSUserDefaults` in `System/Library/Frameworks/Foundation.framework/Headers/NSUserDefaults.h` line 144. The header carries no `NS_SWIFT_SENDABLE` and `Foundation.apinotes` adds none at its `NSUserDefaults` entry, line 969.

So `AppGroupSettingsReader` is a struct with no stored properties. It holds the suite name as a static `String` and opens `UserDefaults(suiteName:)` inside every read. No `@unchecked Sendable`, no `nonisolated(unsafe)`.

That also settles freshness. `reload()` has no cached copy to invalidate, so its body is empty. Measured on this Mac, since the mechanism is the same CFPreferences client that iOS uses: a process reads a suite, an external `defaults write` changes a key, and a read afterwards returns the new value both through a newly built `UserDefaults(suiteName:)` and through an instance held across the write. Two successive external writes, 1.75 then 0.5, were both picked up. `UserDefaults(suiteName:)` also returns a different object each call, so holding one was never an option anyway. The throwaway domain was removed afterwards. On-device confirmation belongs to I1 and Q1.

`synchronize()` is not called. The SDK header comment at `NSUserDefaults.h` line 371 says "this method is unnecessary and shouldn't be used".

## What I1 must wire

- Build one `AppGroupSettingsReader()` and hand the same value to `KeyboardModel` and to `ComposerDriver`.
- `ComposerDriver(adapter:provider:settings:shortcuts:)` takes K2's `InsertionAdapter`, the `PredictionProvider` that K4 and K5 feed through K6, the settings reader, and K4's expander. Pass the driver to `KeyboardModel(actions:)`.
- Declare the conformance `extension <K4 lexicon provider>: ShortcutExpander {}` so one object is both the provider and the expander. K3 does not reference K4's type.
- Call `driver.reloadSettings()` wherever `model.reloadSettings()` is called, on appear and on foreground. The order of the two does not matter, since the driver reloads the reader itself.
- Call `driver.reset()` when the keyboard goes away. It touches no proxy, so it is safe in `viewWillDisappear` and in `deinit`-adjacent paths.
- Nothing extra is needed for page changes. `KeyboardModel.perform` already forwards `.switchKeyboard`, `.nextSymbolPage` and `.dismiss` to `handle`, and the driver flushes on all three.
- The driver plays no feedback. `KeyboardModel` plays it before forwarding, which is the K1 contract.

## What K4 must wire

- Implement `func expansion(textBeforeCursor: String, composing: String) -> PredictionCandidate?` on the lexicon provider. Returning nil means no expansion.
- Use the ruling above for `replacedLength`. A shortcut that matches only the word being composed returns `replacedLength: 0`, since the composing text is always replaced in full.
- Do not append a space to `insertion`. The driver runs the space key's own effect after the expansion, so v1.1's `autocomplete` behaviour of inserting `completion + " "` would double it.
- The expander is asked before space, return, punctuation plain text and the punctuation cycle, and only there.

## What K6 must wire

- Read `driver.candidates`. It is `@Observable`, refreshed after every handled action and after `apply(_:)`, and empty while the prediction setting is off, so the bar needs no separate gate.
- A tap on a candidate calls `driver.apply(candidate)`. The bar must not touch the adapter itself.
- Same `replacedLength` ruling.
