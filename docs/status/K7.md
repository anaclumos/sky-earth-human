## What was built

### SystemFeedbackPlayer

`@MainActor final class SystemFeedbackPlayer: FeedbackPlayer`, `init(settings: any SettingsReader, hapticView: UIView)`, conforming to the protocol K1 declared in `keyboard/KeyboardModel.swift`.

- `play(_:)` calls `UIDevice.current.playInputClick()` unconditionally for every `FeedbackKind`. Apple's documentation, quoted in `docs/spikes/S4.md`, states `playInputClick()` "plays the standard system keyboard click" and defers to the user's Settings > Sounds > Keyboard Clicks preference; per the plan's Sound decision (`PLAN.md` Decisions table) there is no in-app sound toggle and no per-kind sound.
- Haptic: `guard settings.isHapticFeedbackEnabled, let hapticView else { return }` is evaluated inside `play(_:)`, at play time, not cached at init, so a settings reload takes effect without rebuilding the player.
- `hapticView` is a required `init` parameter, stored as `private weak var hapticView: UIView?` to avoid a retain cycle with the view I1 hands it. There is no settable fallback property. If the weakly held view has been deallocated by the time `play(_:)` runs, the guard above returns before any generator is created, the haptic is skipped, and the deprecated no-view initializer is never used as a silent substitute.

### Haptics API chosen, with source

Checked the live iOS 27 SDK headers under `DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer`, not from memory:

- `iPhoneSimulator.sdk/System/Library/Frameworks/UIKit.framework/Headers/UIFeedbackGenerator.h`: the base class's plain `- (instancetype)init` carries `API_DEPRECATED_WITH_REPLACEMENT("+feedbackGeneratorForView:", ios(10.0, API_TO_BE_DEPRECATED))`.
- `iPhoneSimulator.sdk/.../UIImpactFeedbackGenerator.h`: `- (instancetype)initWithStyle:(UIImpactFeedbackStyle)style` carries `API_DEPRECATED_WITH_REPLACEMENT("+feedbackGeneratorWithStyle:forView:", ios(10.0, API_TO_BE_DEPRECATED))`. The replacement, `+ (instancetype)feedbackGeneratorWithStyle:(UIImpactFeedbackStyle)style forView:(UIView *)view API_AVAILABLE(ios(17.5))`, is `NS_SWIFT_NAME(init(style:view:))`, i.e. `UIImpactFeedbackGenerator(style:view:)` in Swift, and requires a view.
- `+feedbackGeneratorWithStyle:forView:` is `API_AVAILABLE(ios(17.5))`. The project's deployment target is iOS 17.0 on every target (`IPHONEOS_DEPLOYMENT_TARGET = 17.0` in every build configuration in `sky-earth-human.xcodeproj/project.pbxproj`), so the view-attached initializer is not always available.

Chosen implementation in `play(_:)`:

```swift
guard settings.isHapticFeedbackEnabled, let hapticView else { return }
let generator = if #available(iOS 17.5, *) {
  UIImpactFeedbackGenerator(style: .light, view: hapticView)
} else {
  UIImpactFeedbackGenerator(style: .light)
}
generator.impactOccurred()
```

The guard is the only place a missing view is handled, and it skips the haptic rather than falling back to a deprecated call. Once past the guard, `hapticView` is a real, non-optional `UIView`, so the branch below it is purely on OS availability: the current, non-deprecated, view-attached initializer on iOS 17.5+, the deprecated style-only initializer on 17.0 through 17.4, since the project's deployment target is 17.0 and the view-attached initializer does not exist below 17.5. The deprecated path does not produce a build warning under this SDK: `os/availability.h` defines `API_TO_BE_DEPRECATED` as the sentinel version `100000`, which the compiler does not treat as reached by any real deployment target, confirmed by reading `iPhoneSimulator.sdk/usr/include/os/availability.h` directly and by the zero-warning build result below.

## What I1 must wire

1. **Placement follows Apple's documentation, not simulator evidence.** S4 (`docs/spikes/S4.md`) tested its click-input view, `ClickInputView`, both as an ordinary subview of `self.view` (Variant A) and assigned directly to `self.inputView` (Variant B). On the simulator, `usesKeyClicks` stayed `NO` and no `systemsoundserver-simd` activity was observed for `playInputClick()` under either placement; S4's own finding states the simulator result is identical across both, so the simulator does not distinguish the two placements. The reason to use the `inputView` placement is Apple's documentation, not simulator measurement: `UIInputViewController.inputView`'s discussion says "To display your keyboard's user interface, add controls and views to the inputView property," and `UIInputViewAudioFeedback`'s overview says to implement the protocol in the view class associated with the custom input nib. I1 must assign `KeyboardInputView` to `UIInputViewController.inputView` directly, e.g. `self.inputView = keyboardInputView`, before adding any other views as its subviews. Whether the placement matters on real hardware, where `usesKeyClicks` may behave differently than on the simulator, is an open question left to the owner device check below, not something S4 or this node measured either way.
2. **Create the input view first, then construct the player with it.** `SystemFeedbackPlayer.init` requires `hapticView: UIView` as a non-optional parameter, so the order matters: create `KeyboardInputView`, assign it to `self.inputView`, and only then construct `SystemFeedbackPlayer(settings: someSettingsReader, hapticView: thatSameView)`. There is no settable property and no fallback path for a missing view; the type requires one at construction.
3. Pass the constructed `SystemFeedbackPlayer` into `KeyboardModel.init(feedback:)`.

## Fix: one generator per press (2026-09-21)

Finding, from an independent verifier:

- Report: `scratchpad/verify-I1b/final-report.md` section m1.
- Evidence: `scratchpad/verify-I1b/logs/mem-M1-samples.txt` and the heap logs next to it.
- `UIImpactFeedbackGenerator` went from 1,783 to 2,383 live instances after exactly 600 presses, about 320 bytes per press.
- Root cause, confirmed by reproduction below: `play(_:)` built a new `UIImpactFeedbackGenerator` on every call (old lines 18-23), never stored a reference past the call, never reused it.

### Documented API facts relied on

| Type / member | Fact | Source |
| --- | --- | --- |
| `UIFeedbackGenerator` | "Don't subclass or create instances of this class yourself. Instead, instantiate one of the concrete feedback generator subclasses." | https://developer.apple.com/documentation/uikit/uifeedbackgenerator |
| `UIFeedbackGenerator.init(view:)` | "Creates a feedback generator and attaches it to the specified view." Available iOS 17.5+. | https://developer.apple.com/documentation/uikit/uifeedbackgenerator/init(view:) |
| `UIFeedbackGenerator.prepare()` | "Prepares the generator to trigger feedback." | https://developer.apple.com/documentation/uikit/uifeedbackgenerator/prepare() |
| `UIImpactFeedbackGenerator` overview sample | Stores one generator as a property (`var feedback = UIImpactFeedbackGenerator()`), assigns it once in `viewDidLoad()` via `UIImpactFeedbackGenerator(view: view)`, calls `prepare()` at gesture start, then calls `impactOccurred(...)` on that same instance for every later collision. One instance, many triggers, never recreated per event. | https://developer.apple.com/documentation/uikit/uiimpactfeedbackgenerator |
| `UIImpactFeedbackGenerator.impactOccurred()` | "Triggers impact feedback." No stated restriction on calling it more than once on the same instance. | https://developer.apple.com/documentation/uikit/uiimpactfeedbackgenerator/impactoccurred() |

Apple's docs do not state whether a view-attached generator is retained by its view. `init(view:)`'s page carries no discussion section beyond the sentence above. The reproduction below is the evidence for the leak, not a documented retain rule.

### Fix

`keyboard/Feedback/SystemFeedbackPlayer.swift`:

- One `UIImpactFeedbackGenerator` is built in `init`, stored as `private let generator`, reused for every `play(_:)` call.
- `hapticView` is no longer stored. It is used once, at construction, to pick the view-attached initializer when available.
- `play(_:)` now calls `generator.prepare()` then `generator.impactOccurred()` on the cached instance, matching the documented sample's shape.
- Public surface unchanged. `init(settings:hapticView:)` and `play(_:)` keep the same signatures. No caller in this branch needs a change.
- Ownership is pinned by the type itself: `generator` is a `private let`, so the compiler forbids reassigning it after `init`. There is no code path left that could build a second instance. The before and after heap counts below are the evidence that this holds at runtime, not a unit test, since a test comparing the identity of a `let` across calls cannot fail and would be a false green.

Behavior change, noted not fixed: the old code skipped the haptic if the weakly held `hapticView` had deallocated by play time. The new code builds the generator once at construction, so a haptic still fires even if the view were to deallocate later. The real composition root, owned by I1 and not present on this branch, ties the player's lifetime to the same view it hands in, so this case does not arise in the shipped wiring.

### Reproduction, before and after

Method:

- `scratchpad/spikes/K7-fix/` compiles the shipped `SystemFeedbackPlayer.swift` unmodified, plus a minimal `FeedbackKind` / `SettingsReader` stand-in, into a UIKit command-line binary for `arm64-apple-ios17.0-simulator`.
- The binary runs via `xcrun simctl spawn` on a dedicated `k7fix-phone` simulator, iOS 27.0.
- It pauses on a control FIFO so the same process can be measured twice, and calls `play(.input)` 600 times between the two pauses.
- `heap <pid> | grep UIImpactFeedbackGenerator` on the simulator process gives the live count at each pause.

| --- | --- | --- | --- | --- |
| `UIImpactFeedbackGenerator` live | 0 | 600 | 1 | 1 |
