## App Group contract (verbatim, shared with downstream keyboard nodes)

Suite name: `group.sh.cho.sky-earth-human.settings`

| Key | Type | Default | Values |
| --- | --- | --- | --- |
| `keySize` | String | `medium` | `small`, `medium`, `large` |
| `isHapticFeedbackEnabled` | Bool | true | |
| `isPredictionEnabled` | Bool | true | |
| `cycleLockSeconds` | Double | 1.0 | 0.5 to 2.0 in steps of 0.25 |

`SettingsModel` (`app/Settings/SettingsModel.swift`) is `@Observable @MainActor`. It opens `UserDefaults(suiteName: "group.sh.cho.sky-earth-human.settings")` once on `init()`, reads each key with the default above as fallback, and writes the raw key on every `didSet` of the corresponding property. `KeySize` is a `String` raw-value enum (`small`/`medium`/`large`) so the stored value matches the contract exactly. Nothing else in the app or keyboard target owns these key names. K3 (`keyboard/Settings/**`) reads the same four keys from the same suite.

## Simulator verification

### Devices

Build for install used a second, signed build (default `CODE_SIGN_STYLE = Automatic`, `DEVELOPMENT_TEAM = QKPXP9788L`, no `CODE_SIGNING_ALLOWED=NO`) targeted at a concrete simulator destination, since the gate's `CODE_SIGNING_ALLOWED=NO` build cannot be installed with `simctl install` (no signature at all).

A shared simulator on this Mac was already running other nodes' work mid-verification (a second app process, `sh.cho.k1host`, was observed interrupting the same booted "iPhone 17 Pro" device, and a stale build of `sh.cho.sky-earth-human` at `CFBundleShortVersionString 1.1`, the archived v1.1 app, not this node's build, was found installed there from another node's run). To get a clean, uncontaminated result, verification moved to a dedicated simulator created for this node:

```
xcrun simctl create h1-verify com.apple.CoreSimulator.SimDeviceType.iPhone-17-Pro com.apple.CoreSimulator.SimRuntime.iOS-27-0
xcrun simctl boot <h1-verify-udid>
```

UDID used below: `ABB72EAA-F8FA-42C5-AB81-C544ADCF1BB1`.

### Signing needed for the group container

Default automatic signing with team `QKPXP9788L` did not fail. `xcodebuild -showBuildSettings` for a simulator destination resolves `CODE_SIGN_IDENTITY = -` ("Sign to Run Locally"), `PROVISIONING_PROFILE_REQUIRED = NO`, `AD_HOC_CODE_SIGNING_ALLOWED = YES`. The simulator does not need a real provisioning profile or an Apple ID login, only the ad hoc identity.

That ad hoc signature's own entitlements blob is empty (confirmed with `codesign -d --entitlements <file> --xml sky-earth-human.app` then `plutil -p`, which printed `{}`). Despite that, `simctl install` still created and linked the App Group container (confirmed empirically below), because the App Group entitlement is not read from the code-signature entitlements blob on the simulator. Xcode also writes the real entitlements plist (`application-identifier = QKPXP9788L.sh.cho.sky-earth-human`, `com.apple.security.application-groups = [group.sh.cho.sky-earth-human.settings]`) into the unsigned `(__TEXT,__entitlements)` Mach-O section of the binary. This is what Apple calls the "simulated entitlements" and is what CoreSimulator actually honors for capabilities like App Groups on Simulator installs, since an ad hoc signature cannot carry a cryptographically verified entitlement the way a provisioning-profile-backed device build does.

Verified with:

```
otool -l sky-earth-human.app/sky-earth-human | grep -A5 'sectname __entitlements'
dd if=sky-earth-human.app/sky-earth-human bs=1 skip=<offset> count=<size> | plutil -p -
```

which decoded to:

```
{
  "application-identifier" => "QKPXP9788L.sh.cho.sky-earth-human"
  "com.apple.security.application-groups" => [
    0 => "group.sh.cho.sky-earth-human.settings"
  ]
}
```

Citation: Apple Developer Forums, DTS Engineer answer on entitlements on iOS Simulator ("Entitlements on the simulator are weird ... instead we simulate the entitlements ... To see the simulated entitlements you have to use `otool` to dump the `__TEXT` / `__entitlements` section"): https://developer.apple.com/forums/thread/733449

No default-signing failure occurred on this Mac. Nothing here required interactive Apple ID sign-in or a manually created provisioning profile.

### XCUITest

Driven from a throwaway project at `<scratchpad>/h1uitest` (`Runner` dummy host app + `RunnerUITests` UI testing bundle, outside the repo, not committed). The test:

```swift

```

Each `"<...>"` placeholder above is the literal Korean accessibility label from `app/Settings/SettingsView.swift`. This file omits the literal Hangul by contract but the strings match the source exactly.

Run with `xcodebuild test -project h1uitest.xcodeproj -scheme Runner -destination 'id=ABB72EAA-F8FA-42C5-AB81-C544ADCF1BB1'`. Test passed. Final on-screen state confirmed the large segment selected, the haptics switch value `0`, and the stepper's accessibility label showing 1.50 seconds.

One finding worth recording for K2/K3/Q1. `app.switches["<haptics toggle label>"]` resolves the outer, label-carrying accessibility element that SwiftUI's `Form` builds for a `Toggle` row, and tapping that outer element does not reliably flip the control on this iOS 27 beta simulator. The actual interactive `UISwitch` is a second, unlabeled child element. The working query is `app.switches["<label>"].switches.firstMatch.tap()` (descend into the labeled row to the real control), not a tap on the labeled element directly. The segmented `Picker` and `Stepper` did not have this problem. Their buttons are directly tappable.
