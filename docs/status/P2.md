## Why this node exists

`docs/status/K3.md` and `docs/status/K6.md` both close on the same open question: the keyboard target is an app extension with no unit test target, so 18 driver tests and 11 merge tests were written, run and left in scratch SwiftPM packages outside the repository. This node makes the repository run them.

The bundle is host-less on purpose. An app extension cannot be a test host, and the containing app carries none of the keyboard's symbols, so hosting in `sky-earth-human` would buy nothing and would add an install and signing step to every simulator run. With no host, `CODE_SIGNING_ALLOWED=NO` is enough for the gate.

## How the keyboard sources reach the tests

The project is `objectVersion = 77` and both existing folders are `PBXFileSystemSynchronizedRootGroup`s, so adding a source file never edits `project.pbxproj`. That property is kept on both sides of this change.

- A new synchronized root group `keyboardTests` at the repository root holds the test sources. It has no exception set, so every file in the folder is a member of the test target.
- The existing `keyboard` synchronized root group is now listed in the `keyboardTests` target's `fileSystemSynchronizedGroups` as well as the `keyboard` target's. Xcode compiles those sources a second time, into the test bundle. Same module, so the tests see the target's `internal` declarations with no `import` and no `@testable`.
- `keyboard` therefore carries two `PBXFileSystemSynchronizedBuildFileExceptionSet` objects, one per target. The new one excludes `Info.plist` and `keyboard.entitlements`, the same two names the `keyboard` target's set excludes. Without it the extension's `Info.plist` would land in the test bundle and its `NSExtension` dictionary would describe the bundle as a keyboard.
- `keyboard/Assets.xcassets` is deliberately not excepted. `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS = YES` is set at project level, and `KeyStyle+Color.swift`, `KeyboardView.swift` and `PredictionBar.swift` resolve `Color(.keyboardBackground)`, `Color(.primaryKeyboardButton)` and `Color(.secondaryKeyboardButton)` through the symbols it generates. Dropping the catalog would stop the test bundle compiling.

Measured, not assumed. `keyboardTests.SwiftFileList` from the gate derived data lists 24 files: all 21 committed `keyboard/**.swift` sources, the generated `GeneratedAssetSymbols.swift`, and the 2 files in `keyboardTests/`. `grep -c 'ComposerDriverTests\|PredictionBarProviderTests' sky-earth-human.xcodeproj/project.pbxproj` is 0, which is the proof that the synchronized group, not a per-file build entry, is what pulls the tests in. The built `keyboardTests.xctest` contains exactly `Assets.car`, a generated `Info.plist` with no `NSExtension` key, and the `keyboardTests` binary.

### Routes considered and rejected

| Route | Why not |
| --- | --- |
| Host the tests in `sky-earth-human` | The app links none of the keyboard's code, so the sources would still have to compile into the test bundle. The host only adds an app install and a signing requirement |
| Move the tested types into a new Swift package | `ComposerDriver` is `@Observable` and `@MainActor` over UIKit protocols, and `PredictionBarProvider` reads `PredictionCandidate` from `KeyboardModel.swift`. Extracting them would move production code that K3 and K6 own, for a test-only reason |
| Keep the scratch SwiftPM packages | They mirror the target's protocols by hand. Any drift between mirror and target is invisible until integration, and neither package runs under any repository gate |

### What changed on the way in

Every `@Test` name, every input and every `#expect` is byte for byte what K3 and K6 ran. The deltas are all outside the test bodies.

| File | Delta | Why |
| --- | --- | --- |
| Both | Dropped `@testable import Driver` and `@testable import PredictionBarKit` | The scratch modules do not exist here. The keyboard sources compile into the same module as the tests |
| Both | Dropped the mirrored protocol blocks | `InsertionAdapter`, `PredictionCandidate`, `PredictionProvider`, `SettingsReader`, `FeedbackKind`, `FeedbackPlayer`, `KeyActionHandler` and `ShortcutExpander` are the real declarations in `keyboard/KeyboardModel.swift` and `keyboard/Composer/ShortcutExpander.swift`. The scratch mirrors were compared against them line by line before deletion and matched exactly |
| `ComposerDriverTests.swift` | `import Synchronization` became `import os`, and `MutableSettings`'s box became `OSAllocatedUnfairLock(initialState: Duration.seconds(1))` instead of `Mutex(Duration.seconds(1))` | `Synchronization.Mutex` is `@available(iOS 18.0)` in the iOS 27.0 SDK and this target deploys to 17.0. `OSAllocatedUnfairLock` and its `init(initialState:)` are `@available(macOS 13.0, iOS 16.0, tvOS 16.0, watchOS 9.0)` in `os.swiftmodule/arm64-apple-ios-simulator.swiftinterface` lines 2394 and 2537, and `withLock` keeps the same `(inout State) -> R` shape, so `MutableSettings` stays `Sendable` with no `@unchecked` and no `nonisolated(unsafe)`. The K3 scratch package deployed to macOS 15, where `Mutex` is available, which is why the question never came up there |
| `PredictionBarProviderTests.swift` | The two stub classes took the repository's swiftformat pass: single-line bodies wrapped, unused parameter labels underscored to `textBeforeCursor _:` and `composing _:` | The K6 package had no `.swiftformat`, so its file had never been linted with this configuration. `swiftformat --lint .` is a gate here |

No test was dropped, renamed or weakened.

## Open questions

| Question | State |
| --- | --- |
| Compiling the keyboard sources twice | Every `keyboard/**.swift` file is compiled once for the appex and once for the test bundle. That is the cost of a same-module test target for an app extension. It also means a source file that only compiles under the extension's own settings would break the test build, which is a feature here, not a risk, since both targets run Swift 6 with complete concurrency at iOS 17.0 |
| `MutableSettings` and iOS 18 | If the deployment target ever moves to iOS 18, `OSAllocatedUnfairLock` in `ComposerDriverTests.swift` can go back to `Synchronization.Mutex`, which is what K3 wrote. Nothing else in the file depends on the choice |
| No test plan file | The scheme keeps `shouldAutocreateTestPlan = "YES"` and carries the testable inline, matching how the rest of the project is configured. If a future node wants parallel destinations or a code coverage target, that becomes an `.xctestplan` and a `TestPlans` block |
| Coverage of the rest of the keyboard target | Only `ComposerDriver` and `PredictionBarProvider` have tests here, because those are the two suites that existed. `LexiconPredictionProvider`, `CompletionPredictionProvider`, `KeyboardModel`, `HeightController` and `SystemFeedbackPlayer` now have somewhere to be tested, and are not |
