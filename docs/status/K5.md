```swift
public struct CompletionFilter: Sendable {
  public struct Completion: Equatable, Sendable {
    public let word: String
    public let replacedLength: Int

    public init(word: String, replacedLength: Int)
  }

  public let fragment: String
  public let composing: String

  public init(textBeforeCursor: String, composing: String)

  public var partialWords: [String] { get }

  public func completions(
    from candidates: [String],
    limit: Int,
    canExtend: (String) -> Bool
  ) -> [Completion]
}
```

Rules, each pinned by a test in `CompletionFilterTests.swift`.

| Rule | Behaviour |
| --- | --- |
| Fragment | The tail of `textBeforeCursor` after the last `Character.isWhitespace`, the same split K4 uses. Trailing whitespace gives an empty fragment |
| Partial words | `fragment` plus `composing` with zero, one and two trailing Characters removed, in that order, empty and duplicate partials skipped. Characters are dropped from `composing` before the concatenation, so a Character that spans the seam cannot hide a partial |
| Prefix | A candidate must `hasPrefix(fragment)`, a Character comparison, so committed text is never rewritten |
| Remainder | `canExtend` is called with the candidate minus `fragment.count` leading Characters |
| Current word | A candidate equal to `fragment + composing` is dropped |
| Duplicates | Dropped, the first position wins. A rejected candidate is remembered too, so `canExtend` runs once per distinct candidate |
| Order and cap | Source order is kept, and the loop stops once `limit` candidates are shown, so `canExtend` is not called for the rest. `limit` 0 or less shows nothing |
| `replacedLength` | `fragment.count`, the composing text is always replaced in full by the driver |

`keyboard/Predictions/CompletionPredictionProvider.swift` in full, verbatim.

```swift
import HangulEngine
import UIKit

@MainActor
final class CompletionPredictionProvider: PredictionProvider {
  private let limit: Int
  private let source: @MainActor (String) -> [String]
  private let canExtend: @MainActor (String) -> Bool

  init(
    limit: Int = 3,
    source: @escaping @MainActor (String) -> [String],
    canExtend: @escaping @MainActor (String) -> Bool
  ) {
    self.limit = limit
    self.source = source
    self.canExtend = canExtend
  }

  convenience init(limit: Int = 3, canExtend: @escaping @MainActor (String) -> Bool) {
    let checker = UITextChecker()
    self.init(
      limit: limit,
      source: { partial in
        checker.completions(
          forPartialWordRange: NSRange(location: 0, length: partial.utf16.count),
          in: partial,
          language: "ko_KR"
        ) ?? []
      },
      canExtend: canExtend
    )
  }

  func candidates(textBeforeCursor: String, composing: String) -> [PredictionCandidate] {
    let filter = CompletionFilter(textBeforeCursor: textBeforeCursor, composing: composing)
    let found = filter.partialWords.flatMap { source($0) }
    return filter.completions(from: found, limit: limit) { canExtend($0) }.map {
      PredictionCandidate(display: $0.word, replacedLength: $0.replacedLength, insertion: $0.word)
    }
  }
}
```

- `display` and `insertion` are the completed word. `replacedLength` comes from the filter.
- Nothing composing and an empty fragment gives no partial word, so the source is never asked and the result is empty.
- No cache, no queue, no stored state beyond the three `let`s.

### Normalization

Every candidate in every run is NFC. The probe compares each candidate's scalars to `precomposedStringWithCanonicalMapping`, and the per-row flag was true on all 36 Korean rows of each of the three runs, 108 rows, 0 false. No normalization is applied in the provider or the filter. The engine compares scalars and emits precomposed syllables, the fragment reaches `hasPrefix` which compares Characters, and the remainder handed to `canExtend` is cut from the candidate, so it is NFC whenever the candidate is.

```swift
func points(_ text: String) -> String {
  let listed = text.unicodeScalars.map { "U+" + String($0.value, radix: 16, uppercase: true) }
  return listed.isEmpty ? "EMPTY" : listed.joined(separator: " ")
}

func isNFC(_ text: String) -> Bool {
  Array(text.unicodeScalars) == Array(text.precomposedStringWithCanonicalMapping.unicodeScalars)
}

func micros(_ duration: Duration) -> Double {
  let parts = duration.components
  return Double(parts.seconds) * 1_000_000 + Double(parts.attoseconds) / 1_000_000_000_000
```

## What I1 must wire

1. Construction order, because the provider's closure needs the driver and the driver's init needs the provider. Build the provider first with a closure that reaches the driver through a weak reference to the object that will own it, then build the driver, then store it. In `KeyboardViewController` that is

```swift
let completions = CompletionPredictionProvider { [weak self] text in
  self?.driver?.canExtend(to: text) ?? false
}
let driver = ComposerDriver(adapter: adapter, provider: <K6 bar provider over lexicon and completions>, settings: settings, shortcuts: lexicon)
self.driver = driver
```

   The controller owns the driver, the driver owns the provider, the provider owns the closure, and the closure holds the controller weakly. The harness above confirmed the driver deallocates with its owner under exactly this shape. Never capture the driver strongly in the closure.
2. `?? false` is only reached when the controller is gone. With a live driver the engine answers true while idle, so the fallback never shapes a visible list.
3. Keep the default `limit` of 3 unless K6 asks for another number. The bar shows three slots and K4's shortcut takes slot one when present, so K6 may prefer to ask this provider for 3 and trim after the merge.
4. Pass `adapter.textBeforeCursor` and `session.composing` exactly as `ComposerDriver.refreshCandidates()` already does. Marked text must not be in `textBeforeCursor`, which S2 measured is how the proxy behaves.
5. Build one provider for the life of the controller. Its `UITextChecker` is created once in the convenience init.
6. The first `completions` call in the process costs 58 ms to 2.07 s on the simulator, 50 ms to 1.46 s in the verifier's runs. Ruling after the verifier: I1 makes one warm up call in `viewDidLoad`, for example `_ = completions.candidates(textBeforeCursor: "\u{D558}", composing: "")` through the provider or one direct `UITextChecker` query, so the cost lands before the first key press. Nothing in this node does it.

## What K6 must wire

1. `candidates(textBeforeCursor:composing:)` returns 0 to `limit` candidates in the checker's order. This node kept that order and did not characterize it.
2. `display` and `insertion` are the same string. Render `display`, insert `insertion`, carry `replacedLength` through to `driver.apply(_:)` untouched.
3. A candidate from this provider never equals the word as typed, so the bar never shows a no-op.
4. The list changes on every press and is empty on a press that leaves nothing to complete. Nothing here is sticky.

## For the owner's S5 device check

Stated as what the simulator did, to be compared on a physical device.

- `UITextChecker.availableLanguages` on the device contains `ko_KR`.
- `completions(forPartialWordRange:in:language:)` with `ko_KR` returns candidates for U+D558, U+D56B, U+C548 U+B155 and a lone U+3131, without enabling a Korean keyboard and without `learnWord`.
- Every candidate is NFC. If the device returns decomposed jamo, every candidate is rejected while composing and the bar stays empty. The fix is one `precomposedStringWithCanonicalMapping` on each candidate in the convenience init.
- The first call in the extension process, and the warm per call cost. The simulator ran on Apple silicon, so a device will be slower by an unknown factor.
- Whether the keyboard extension sandbox, with `RequestsOpenAccess` false, is allowed to reach the checker at all. The probe ran as a plain process, not inside an extension.

## Open questions

| Question | State |
| --- | --- |
| First call cost | 58 ms to 2.07 s on the simulator, once per process, on the main thread. Ruled: I1 warms it up in `viewDidLoad`, see I1 item 6 |
| Lone consonant queries | The most expensive query, 5.6 to 11.8 ms, is the single query for a lone consonant partial such as U+3131, so a cap on the query count would not touch it. | Word boundary | The fragment splits on whitespace only, matching K4.
