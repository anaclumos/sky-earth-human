## ShortcutMatcher surface

Public declarations of `Packages/HangulEngine/Sources/HangulEngine/ShortcutMatcher.swift`, verbatim, bodies elided. The file holds one private stored property and two private static helpers beyond these.

```swift
public struct ShortcutMatcher: Sendable {
  public struct Entry: Equatable, Sendable {
    public let userInput: String
    public let documentText: String

    public init(userInput: String, documentText: String)
  }

  public struct Expansion: Equatable, Sendable {
    public let replacement: String
    public let replacedLength: Int

    public init(replacement: String, replacedLength: Int)
  }

  public init(entries: [Entry])

  public func expansion(textBeforeCursor: String, composing: String) -> Expansion?
}
```

Behavior:

- `init(entries:)` keeps only the pairs whose two sides differ. S1 established that a Text Replacement shortcut is recognizable only because `userInput` differs from `documentText`, and that every contact derived entry comes back with the two sides equal. The plan's decision table keeps anything beyond Text Replacement out of 2.0, so the equal pairs are dropped. The comparison there is on the raw strings, not the folded ones, because the S1 Hangul shortcut has `userInput` U+3131 U+314F against `documentText` U+AC00 and folding first would erase that difference and discard a real shortcut.
- `init(entries:)` also drops any entry whose `userInput` holds whitespace. The current word never holds whitespace, so such an entry is unreachable, and dropping it makes that guarantee hold by construction instead of depending on what the engine puts in `composing`.
- The current word is the tail of `textBeforeCursor` after the last whitespace, followed by `composing`. `composing` is marked text and is not part of `textBeforeCursor`, which S2 measured. The split uses `Character.isWhitespace`, which covers tab and newline as well as space. The tests assert space, U+000A, and U+0009 all break the word.
- `expansion(textBeforeCursor:composing:)` answers an exact match of the current word against a `userInput`. No prefix match, no fuzzy match.
- `replacedLength` counts Characters of committed text before the cursor only. The composing text is replaced in full on top of that, so it is excluded from the count. A shortcut typed entirely as marked text reports `replacedLength` 0.
- An empty current word never matches, so a cursor sitting after a space produces no candidate even if the lexicon carries an entry with an empty `userInput`.
- Duplicate `userInput` values collapse, last entry wins.

## LexiconPredictionProvider surface

`keyboard/Predictions/LexiconPredictionProvider.swift` in full, verbatim.

```swift
import HangulEngine
import UIKit

@MainActor
final class LexiconPredictionProvider: PredictionProvider {
  private var matcher = ShortcutMatcher(entries: [])

  func update(with lexicon: UILexicon) {
    matcher = ShortcutMatcher(
      entries: lexicon.entries.map {
        ShortcutMatcher.Entry(userInput: $0.userInput, documentText: $0.documentText)
      }
    )
  }

  func candidates(textBeforeCursor: String, composing: String) -> [PredictionCandidate] {
    guard let candidate = expansion(textBeforeCursor: textBeforeCursor, composing: composing) else { return [] }
    return [candidate]
  }

  func expansion(textBeforeCursor: String, composing: String) -> PredictionCandidate? {
    guard let match = matcher.expansion(textBeforeCursor: textBeforeCursor, composing: composing) else { return nil }
    return PredictionCandidate(
      display: match.replacement,
      replacedLength: match.replacedLength,
      insertion: match.replacement
    )
  }
}
```

- `candidates(textBeforeCursor:composing:)` returns zero or one candidate.
- `display` and `insertion` both carry the `documentText`. `replacedLength` comes from the matcher.
- `expansion(textBeforeCursor:composing:)` carries the same result for K3's `ShortcutExpander` protocol. This file names no K3 type. I1 declares the conformance.
- No cache, no stored lexicon, no invalidation. `update(with:)` replaces the matcher outright.

## Case decision

Matching is case insensitive. This is Apple's documented behavior, not a choice.

`UILexicon.h` in `iPhoneOS27.0.sdk`, lines 17 through 20, reading
`/Applications/Xcode-beta.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS27.0.sdk/System/Library/Frameworks/UIKit.framework/Headers/UILexicon.h`:

```
// -documentText returns the intended text to be inserted into the document for a given -userInput.
// -userInput represents the expected typed string, which need not match the actual typed string.
// for example, if the -documentText were "iPhone", the corresponding -userInput could be "iphone"
// -the documentText may also be in a different text script from the -userInput
```

- The header states outright that `userInput` need not match the string the user typed, and the one example it gives is a case difference.
- The published pages for [UILexiconEntry](https://developer.apple.com/documentation/uikit/uilexiconentry), [userInput](https://developer.apple.com/documentation/uikit/uilexiconentry/userinput) and [documentText](https://developer.apple.com/documentation/uikit/uilexiconentry/documenttext) say nothing about case. The header is the only statement on the matter, so it is the one cited.
- The fold is `lowercased()`, which is the Unicode default full case mapping and is locale independent, so a Turkish locale cannot change the result.
- The last line of that header comment also rules out requiring the two sides to share a script, which is what the Hangul entries in S1 look like.

## Normalization decision

The comparison folds both sides through NFKC, `precomposedStringWithCompatibilityMapping`. NFC is not enough and no normalization at all fails outright.

Reason. S1 captured a Text Replacement shortcut whose `userInput` is U+3131 U+314F, compatibility jamo, while its `documentText` is U+AC00. The engine renders that same syllable precomposed as U+AC00, per the rendering contract in `PLAN.md` and `RenderingTests.swift`. Without a fold the typed word and the stored shortcut never compare equal.

Measured with Foundation on the pinned toolchain, not taken from documentation:

| Input | Raw | NFC | NFKC |
| --- | --- | --- | --- |
| Compatibility jamo pair | U+3131 U+314F | U+3131 U+314F | U+1100 U+1161 |
| Precomposed syllable | U+AC00 | U+AC00 | U+AC00 |
| Lone compatibility jamo | U+3131 | U+3131 | U+1100 |
| Pending araea after an initial | U+1100 U+119E | U+1100 U+119E | U+1100 U+119E |
| Pending double araea after an initial | U+1100 U+11A2 | U+1100 U+11A2 | U+1100 U+11A2 |
| Araea with no initial | U+119E | U+119E | U+119E |

- NFKC of the compatibility jamo pair equals NFKC of the precomposed syllable. NFC of the two is not equal, and the raw strings are not equal.
- NFKC leaves both pending araea sequences exactly as the engine emits them. U+119E and U+11A2 carry no decomposition mapping, and the Unicode Hangul composition step only joins a leading jamo with a medial in U+1161 through U+1175, so neither sequence collapses into a syllable. The requirement not to turn a pending araea into something else holds, and `ShortcutMatcherTests.swift` pins it with a test that keeps U+1100 U+119E, U+1100 U+11A2, and U+AC00 distinct from one another.
- NFKC is applied symmetrically to the stored `userInput` and to the typed word, so a lone compatibility jamo still matches a lone compatibility jamo even though both move to the U+1100 block inside the fold.
- Cost of NFKC beyond Hangul. It also folds compatibility forms such as ligatures and full width Latin, so U+FB01 folds to U+0066 U+0069. For matching a Text Replacement shortcut that is the wanted behavior, since a user who stored a shortcut in one compatibility form should still reach it after typing the plain form.

## What I1 must wire

1. Build one `LexiconPredictionProvider` in the composition root and keep it for the life of the controller.
2. Call `requestSupplementaryLexicon` in `viewWillAppear` on every appearance and call `update(with:)` from the completion. No first-appearance guard, no caching. That is the whole refresh policy, and S1 is the reason. A shortcut added while the keyboard stays up was absent from the first automatic `viewWillAppear` after returning from Settings and present on the next one about five seconds later, so a single request on first appearance would serve a stale list for the rest of the session.
3. The completion runs on the main actor, so `update(with:)` is callable from inside it with no hop. `UIInputViewController` carries `NS_SWIFT_UI_ACTOR` in the SDK header. Verified by type checking a throwaway subclass that captures a `@MainActor` type inside the completion, with `-swift-version 6 -strict-concurrency=complete` against the iOS 17.0 simulator SDK, exit 0.
4. Declare the conformance to K3's `ShortcutExpander`. `expansion(textBeforeCursor:composing:)` already has the required signature, so an empty extension is enough.
5. Feed `textBeforeCursor` from the `InsertionAdapter` and `composing` from the engine driver. Passing marked text inside `textBeforeCursor` would double count the word and produce a wrong `replacedLength`.
6. Applying a candidate means deleting `replacedLength` Characters of committed text, then clearing the marked text, then inserting `insertion`. `replacedLength` never covers the composing text.

## What K6 must wire

1. Treat this as the shortcut source for slot one of the three-slot bar, per the K4 row in `PLAN.md`.
2. `candidates(textBeforeCursor:composing:)` returns at most one element, so slot one is either that candidate or empty. K5's completions fill the rest.
3. `display` and `insertion` are the same string, the `documentText`. Render `display`, insert `insertion`.
4. Carry `replacedLength` through to whatever applies the candidate. Recomputing it in the bar would be wrong, since only the matcher knows how much of the word was committed.
5. Hide the bar when `isPredictionEnabled` is off. This provider has no setting of its own.
