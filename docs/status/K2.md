- The proxy closure runs on every call. The adapter stores no proxy object.
- `selectedRange` on a mark is `NSRange(location: text.utf16.count, length: 0)`, a caret at the end of the marked string.
- The state is the last marked string, whether the host may still hold a mark the adapter did not make, whether a call holds the next run loop turn, and the host's answers the adapter expects. Those are kept as the last view the host sent, the adapter's own calls since then, and which of those calls the host may answer. A call is a mark, an insert, a delete, or an unmark with the proxy view right after it. With no answer expected the calls fold into that view at once. Past 256 calls kept behind expected answers the adapter drops the answers and folds the calls, finding 9, so a host that never answers a newline keeps at most 256 calls. A view that matches no expected answer while a newline is unanswered is held unconfirmed until the next callback or the next `settle()`. The marked string is never read back from `documentContextBeforeInput`.
- A new adapter starts unsettled, and a `hostTextDidChange()` that returns true or holds a view unconfirmed and `endLeftoverMark()` unsettle it again. `ComposerDriver` queues every key and candidate tap while `isSettled` is false, calls `settle()`, and drains the queue in order from `onSettle`. So the first mutation after a creation or a host change is always preceded by one `unmarkText()` in an earlier turn.
- `documentIdentifier` is read through `value(forKey:)`. The SDK declares it non-null, `UIInputViewController.h` line 30 inside `NS_HEADER_AUDIT_BEGIN(nullability, sendability)`, but the system proxy returns nil while the host has sent no document, and the Swift read then traps in `UUID._unconditionallyBridgeFromObjectiveC`, crash reports `~/Library/Logs/DiagnosticReports/Retired/VKeyboard-2026-09-21-080205.ips`, `-080210.ips` and `-080217.ips` from the harness keyboard.
- `replace` with a mark and `n` above zero reads `textBeforeCursor` once, before its first proxy call, and counts the replaced fragment plus the former mark as one string, so a vowel jamo mark that joins the last committed syllable into one `Character` counts once. `CompletionFilter` derives `replacedLength` from the same context, so the two agree on the fragment.
- No commit path calls `unmarkText()`. Verifier finding 1 below is the reason. Two methods call it, and after neither does another proxy mutation follow in the same run loop turn. `endLeftoverMark()`, which the composition root calls from `viewWillDisappear` always and from `viewWillAppear` only when `hasDocument` was true at the last `viewWillDisappear`. `settle()`, which the driver calls before the first mutation after a creation or a host change, and which holds every mutation for a later turn. Neither checks the local mark, because after a host resign or a focus move the local mark may already be forgotten while the host still holds one.
- `hasDocument` separates the exits. On the keyboard's own dismissal and on a background the proxy still holds the document at `viewWillDisappear`. On a host `resignFirstResponder` the host has already fired `textDidChange` with `hasText` false and both contexts nil, and ending the leftover mark on the next appearance would move the caret to the start of the field. The re-check section below has the measurements.
- `deleteBackward()` carries no assert. A local mark that the host already ended is a state desync, not a caller contract violation.
- No fallback path, per `docs/spikes/S2.md`.

Every path is pinned by `keyboardTests/MarkedTextInsertionAdapterTests.swift`, 46 tests over a fake `UITextDocumentProxy` that records each call in order. ### Finding 9, the verifier's major M1 on `eb6475f`, a clearing return handler at human speed

A handler that refuses the newline answers it, and that answer repeats the view of the handler's last change, because both are the host's view once the handler has run. A host clear draws no answer. Remedy, `b5fb29e`.

- While a newline is unanswered, a view that matches no expected answer is held unconfirmed. `hostTextDidChange()` returns false and the adapter is unsettled, so the next key waits for `settle()`.
- A next callback with the same view is the answer to the earliest unanswered newline. That view becomes the host's view and the calls after the newline stay, since the host applies them after its handler. The composition goes on.
- A next callback with another view makes it a host change at once, and the root resets as before.
- A next key first makes it a host change in `settle()`. The adapter forgets its mark and calls `onHostChange`, and the driver drops its composition and keeps the queued key, which then composes afresh after the settle's `unmarkText()`.
- Minor 1. Past 256 calls kept behind expected answers the adapter drops the answers and folds the calls into its view. The largest backlog measured behind a blocking return handler is 103 calls with 9 answers, the slow field burst of finding 8, so the bound leaves every measured late answer matched. A host that never answers keeps at most 256 calls and each callback replays at most 256.
- Minor 2. ## What K3 and I1 must know

- I1 builds the adapter as `MarkedTextInsertionAdapter { [unowned self] in textDocumentProxy }` inside the input view controller. The adapter retains the closure, so a strong capture of the controller that owns the adapter is a retain cycle.
- I1 wires the leftover mark exactly as the harness keyboard did in the conditional pass of the re-check, measured above. The key is one `Bool` in the extension's own `UserDefaults.standard`, name `leftoverDocumentAttached`, and the order inside each override is the order below.

```swift
override func viewWillDisappear(_ animated: Bool) {
  super.viewWillDisappear(animated)
  let attached = adapter.hasDocument
  driver.reset()
  UserDefaults.standard.set(attached, forKey: "leftoverDocumentAttached")
}

// The unmark moved here from viewWillDisappear at d22f22c, docs/status/I1.md QA finding R07.
override func viewDidDisappear(_ animated: Bool) {
  super.viewDidDisappear(animated)
  adapter.endLeftoverMark()
}

override func viewWillAppear(_ animated: Bool) {
  super.viewWillAppear(animated)
  let attached = UserDefaults.standard.bool(forKey: "leftoverDocumentAttached")
  UserDefaults.standard.removeObject(forKey: "leftoverDocumentAttached")
  if attached {
    adapter.endLeftoverMark()
  }
}

override func textDidChange(_ textInput: (any UITextInput)?) {
  super.textDidChange(textInput)
  if adapter.hostTextDidChange() {
    driver.reset()
  }
}
```

- `hasDocument` is read before `endLeftoverMark()`, because the read is what the appearance decision is made on and the call itself must run on every disappearance. Since `d22f22c` `endLeftoverMark()` runs in `viewDidDisappear`, after `driver.reset()`, and nothing in `viewWillDisappear` touches the proxy. Safari calls `viewWillDisappear` before it blurs its input, and an unmark issued there left the input focused with an empty keyboard, `docs/status/I1.md` QA finding R07. `driver.reset()` makes no adapter call, `ComposerDriverTests.resetIsSilent`, so the unmark is still the one proxy call of a disappearance. A `setMarkedText("")` in the same turn as the `unmarkText()` would be finding 1 again. The unit test `disappearThenAppear` pins the call order, `hasDocument` pins the read.
- The appearance call runs before any key is handled and only when the flag was true. After the keyboard's own dismissal the flag is true and the call finds the mark already committed, harmless. After a background the flag is true and the call commits the mark the host kept. After a host `resignFirstResponder` the flag is false and no call is made at appearance, so the caret stays where the refocus tap put it. The host still holds the leftover mark, and the first key's `settle()` commits it there, finding 6. The key is removed on every read so a stale true cannot leak into a later appearance.
- Never call `endLeftoverMark()` from a key handler or from `textDidChange`. In a key handler `unmarkText()` followed by another proxy mutation in the same turn is exactly finding 1. In the `textDidChange` that a host resign fires the proxy has no document, `hasText` false and both contexts nil, so the call would end nothing. On the key path the only `unmarkText()` is the one `settle()` issues, and the driver issues it.
- `textDidChange` calls `adapter.hostTextDidChange()` and resets the driver only when it returns true. The host answers two of the keyboard's own calls with a `textDidChange` that may land after later keys. The committing unmark of `settle()` draws one 4 to 7 ms later in `UITextField`, `UITextView` and `UISearchBar`, finding 6. A newline the field's return handler declines draws one 3 to 19 ms later, or after the handler's whole run time, finding 8. For those the adapter returns false and the composition goes on, so a syllable typed across the answer stays whole. A return handler that changes the text sends that change and then the answer with the same view, before the host applies any key typed since, finding 9. While a newline is unanswered the adapter returns false for a view it cannot yet tell from such a change, holds it, and decides at the next callback or at the next key. A host change decided at the next key reaches the driver through `onHostChange`, not through the root. Anything else returns true, the adapter has already forgotten its mark and unsettled itself, and `driver.reset()` drops the composition and any queued key. The finding 4 table above lists the keyboard's own bulk deletes that also draw a `textDidChange`, and those still reset. The handler must not read the proxy to decide on its own. Only the adapter knows its calls since the host's last view, and the proxy's view after a late answer is the host's old one.
- Nothing in the adapter waits for a host callback. `settle()` holds one run loop turn and `insertReturn()` two, and every key typed meanwhile queues in the driver and drains when the turn ends. An answer that never comes is dropped at the next host change, or once 256 calls wait behind it.
- `K2-fix3` changes no line of the wiring block above. The `InsertionAdapter` protocol gains `onHostChange`, which `ComposerDriver` assigns in its initializer. Like `onSettle`, the composition root never assigns it. A root merged with `b5fb29e` builds unchanged, and a conformer outside `keyboard/`, a fake included, must add the property.
- Only `driver.reset()` may drop keys the driver queued. `onHostChange` drops the composition only and keeps the queued keys, which the host applies after its change. `ComposerDriver` owns `adapter.onSettle` and `adapter.onHostChange` from its initializer, so the composition root never assigns it, and every key and candidate tap must reach the adapter through `driver.handle(_:)` or `driver.apply(_:)`, never directly.
- An in-app field switch, a tap on a second field and then back into the marked field, reaches neither `viewWillDisappear` nor `viewWillAppear`. The verifier measured it at `1d99efc`. Only `textDidChange` fires, and the host keeps the mark. `hostTextDidChange()` returns true there and unsettles the adapter, and the first key back in the marked field settles it, committing the kept mark where the host left it, the move and movetype rows of finding 6. After the switch back onto a kept mark the proxy has no `documentIdentifier` until the host answers that unmark, and the adapter takes the first callback that brings one as that answer.
- A return is `driver.handle(.returnKey)`. The driver flushes the composition and calls `adapter.insertReturn()`, never `commit("\n")`, finding 7. Keys typed during the two turns of a return queue behind it.
- K3 applies an engine `Composition` as `commit(committed)` when `committed` is not empty, then `setComposing(composing)`, both in the same key handler. The MIG and P2 probes measured that shape in seven hosts. `commit` then `commit` in one handler is the P3 and P4 shape, also measured. A return is not a `commit`, see the bullet on `insertReturn()` above.
- `commit` takes the full text that must land as plain text. The adapter removes whatever is marked first, so K3 never needs to know whether the text equals the mark.
- `setComposing` with the string already marked, `setComposing("")` with nothing marked and `commit("")` with nothing marked make no proxy call. K3 can call `setComposing(composing)` after every key without a guard.
- `setComposing("")` with a live mark is `setMarkedText("")`, the same call as `commit("")`, on every path: the engine's backspace to empty, a flush, a replace with nothing committed of the word. It is never a `deleteBackward()`. WebKit's `deleteBackward()` on a live mark removes one grapheme cluster, not the marked string, and a lone vowel jamo mark after a committed syllable is one cluster with that syllable, finding 5 below.
- K6 and K3 apply a candidate through `driver.apply(candidate)`, which flushes the engine and calls `adapter.replace(deleting: replacedLength, with: insertion)`, one operation in one key handler. Shortcut expansions take the same call. The adapter owns the proxy sequence, so the driver stays UIKit agnostic. Every `InsertionAdapter` conformer implements `replace(deleting:with:)`, the fakes under `keyboardTests/` included. Finding 5 measured the sequence in seven hosts over nine mark shapes.
- `replace` with a mark and `replacedLength` above zero needs `textBeforeCursor` to hold the replaced fragment when the handler starts. `CompletionFilter` derives `replacedLength` from the same `textBeforeCursor`, after the last whitespace, so the count and the fragment agree.
- `deleteBackward()` deletes one character of committed text and forgets any local mark. K3 rewinds inside a composition through the engine and `setComposing`. The engine's `Composition` is the only source of composition state.
- `textBeforeCursor` is committed text only and is the empty string on an empty field. It reads the proxy, so after a late answer it lacks the keyboard's calls since the answered one until the next host callback, and after a newline a single line field declined without an answer it still ends in that newline, finding 8 and Host limitations.
- `deleteBackward()` on a committed U+1100 U+119E removed both scalars in `UITextField`, measured at `ff5b2f5`.
